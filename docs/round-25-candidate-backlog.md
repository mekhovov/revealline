# Round 25 candidate — consistent flight controls

Research and source inspection on 12 September 2026, after the v0.14 source freeze. **Proposal only:** no runtime, preference, test fixture or archived release is changed here. The next bounded improvement should make existing solo flight controls consistently comfortable to point at, including wide desktop and hybrid-input layouts. Start with one better default, before adding a mirrored-layout preference.

## Current evidence

The parent's Round 24 source-browser checks found Read/Done/Retry at least 44 CSS pixels in the measured layouts, but the smallest flight controls at 1280×720 were 34×28. At 320- and 390-pixel widths the flight minimum was 44. Some content required vertical scrolling at 844×501. Those observations describe the checked browser, not physical touch hardware or every media-query combination.

The [solo stylesheet](../game/style.css) explains the discontinuity:

| Current rule                                                                   | Consequence                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Base `.direction-controls`: three 34px columns, three 28px rows, 3px gaps      | Wide desktop direction/Stop controls retain small target boxes.                                                                                                                                                                                                              |
| Base `.icon-button`: 34×35; `.button` minimum height 43                        | Pause/restart/sound and action controls have different defaults. Actual rectangles also depend on content and later rules.                                                                                                                                                   |
| Later width ≤ 680, height ≤ 500 with width ≥ 681, and width 681–1100 overrides | These explicitly restore 44px direction tracks and several other control sizes. Wider, taller windows do not get those track overrides.                                                                                                                                      |
| `@media (pointer: coarse)` sets child buttons' minimum width/height to 44      | It does not enlarge the base 34×28 grid tracks at width > 1100 and height > 500. From the declared geometry, adjacent 44px targets can overlap by 7px horizontally and 13px vertically. This is a source-derived risk to reproduce, not an observed physical-device failure. |
| Height reserves 330/380/400 plus a 320px arena minimum in selected layouts     | Enlarging controls can require more vertical space. The existing minimum protects the board from collapsing at narrow/short desktop sizes.                                                                                                                                   |

The [markup](../game/index.html) already supplies real buttons, labels and a stable grouping: directions/Stop, ability/Supply/Boost, then pause/restart/sound. The [input adapter](../game/ui/input.mjs) owns pointer capture, cancellation and Hold/Tap semantics. Resizing these elements should not replace them, move handlers, invert directions or change canonical commands.

## Primary guidance, precisely scoped

[WCAG 2.2 SC 2.5.8, Target Size (Minimum), Level AA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) specifies 24×24 CSS-pixel pointer targets, with spacing, equivalent-control, inline, user-agent and essential-presentation exceptions. A 34×28 button is not automatically an AA failure. Actual target shape, spacing and overlap still matter; keyboard support alone is not the equivalent same-page pointer-control exception.

[SC 2.5.5, Target Size (Enhanced), Level AAA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html) uses 44×44 CSS pixels, with its own exceptions, and recommends larger targets where useful for frequent actions. Use 44 as this game's practical design baseline, not a universal WCAG requirement or a claim of overall AAA conformance.

[Microsoft XAG 107, Input](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/107) supports flexible input, portrait/landscape play, adjustable target size/spacing/position and preset layouts. Its mobile recommendations use physical dimensions and DPI examples; 44 CSS pixels must not be described as meeting its 15mm phone or 24mm tablet guidance. A layout editor could eventually help reach and dexterity needs, but it adds configuration and accessibility work of its own. This proposal addresses the observed default inconsistency first.

Only primary page text was inspected for this note. Embedded images/video and physical devices were not tested. The recommendation is an inference from that guidance and the current code, not a measured improvement in comfort or retention.

## Recommended first increment

1. **Give the existing solo flight controls a shared 44px target baseline.** Use a small set of CSS variables scoped to `.play-controls` for target size and spacing. Set grid tracks and actual button boxes together; a min-size override inside smaller fixed tracks is insufficient. Keep a visible inactive gap between adjacent targets. The existing 144px compact column can hold three 44px targets with 4px gaps; do not silently enlarge it beyond the 320px layout's available space.
2. **Reflow groups around that baseline.** Directions remain a cross with Stop in the center. Ability/Supply/Boost may wrap or stack, and utility controls may become a column or a separate row when needed. Keep DOM/focus order and button identity. Preserve labels and keyboard hints, including long validated class labels. Avoid invisible expanded hit regions, overlapping pseudo-elements, browser zoom tricks or controls over the playing field.
3. **Balance board size against honest vertical scrolling.** Reassess the existing desktop height reserve after measuring the new control group; do not simply add a late global min-height patch or shrink the board until every panel fits. Keep the current 320px minimum where the available column allows it. At short heights, vertical page scrolling is acceptable if the full board and controls remain reachable, essential status stays readable, and there is no horizontal overflow. Check ordinary and Sentinel layouts, including Toggle Boost, retry consequence and appearance notices. Do not claim that everything fits above the fold at 844×501.

This is a CSS-focused solo improvement reused by Playground and Controller practice, with a small markup change only if real measurement requires it. It does not need a saved setting, media-query detection in JavaScript, a new schema, physics changes or a second control implementation. Avoid removing existing compact/coarse rules wholesale; consolidate only the relevant conflicting sizing declarations and verify their final cascade. Couch, Replay Theater and the separate authoring toolbars stay out of scope unless a shared selector demonstrably affects them.

## Acceptance and boundaries

- Measure actual button rectangles and gaps at 320×640, 390×844, 844×390, 844×501 and 1280×720, plus the 1100/1101 width boundary at 720px height. Include the 680/681 transition and tall desktop. Record requested **and actual** iframe viewport values; screenshot pixels and CSS pixels are different when previews are scaled.
- Every visible enabled button in the solo flight-control group should have an actual target at least 44×44 CSS pixels, with no intersecting neighbor target rectangles or clipped labels. Check direction/Stop separately from ability and utility buttons. A pointer-capability emulator is useful only when its reported media matches the intended condition; record hybrid/coarse results separately from real hardware.
- Test actual pointer hits at the center and near the edge of Up/Stop/Down and Left/Stop/Right. One touch must not select a neighbor. Preserve movement release, pointer-cancel/lost-capture behavior, Tap steering/Stop and mixed keyboard/controller control. Keep direction and Boost's existing held-input behavior; this layout change does not redesign activation timing.
- Through the real Controller Lab, join/start, pause, read a long briefing, exit and resume. After actual loss, read the consequence and activate Retry once. Complete an ordinary and a staged mission to inspect full-picture/result controls. Layout must not create a command, change a replay checkpoint or alter a save.
- Preserve native keyboard order/focus visibility and existing named controls. Inspect text enlargement/zoom for clipping and reachability without counting zoom as a replacement for CSS target sizing. No new tests that merely match CSS strings are warranted; actual geometry and interaction observations are the meaningful checks. Run existing input/navigation gates if handlers or markup change, and the usual frozen-release gates when that release is ready.

**Later option, separate decision:** a finite Left/Right touch arrangement could move whole groups without changing physical arrow meanings. It would need a keyboard/controller-accessible settings UI, strict preference migration, portable backups/Undo, neutral clearing on adoption, logical focus order and real reachability tests in both orientations. Arbitrary drag-to-place controls or a full layout editor would be a larger feature. Neither is required to fix the current sizing inconsistency; do not add them to this first increment by implication.
