# Reproduce the FPV environment GPU comparison

This manual browser fixture compares the current renderer against the frozen
parent `b49979e17d8add2518e989f42455619caea08017`. It is outside the runtime packages
and deferred unit-test suite. The checked-in manifest identifies every frozen
input, including the i18n side-effect modules and pinned Three.js/Rapier vendor
files. No downloaded assets, browser driver, branch changes or Git writes are
needed.

From the repository root:

```sh
node scripts/prepare-fpv-environment-verification.mjs --verify-only
node scripts/prepare-fpv-environment-verification.mjs
node scripts/game-cli.mjs serve --port 8789
```

The local clone must already contain the pinned commit. The preparation command
uses `git show` on 29 explicitly allowed paths, verifies every SHA-256 and checks
the literal relative import closure. It copies files, not symlinks; the local
server intentionally rejects symlink paths. It never fetches missing history.
`--verify-only` reads and verifies the snapshot without writing files.

Open
`http://127.0.0.1:8789/dist/fpv-environment-verification/index.html`, click
**Run comparison**, and keep the page visible. Stop editing source until the run
finishes. Click **Download receipt** to preserve the JSON, also available in the
rendered `#receipt` element and `window.fpvEnvironmentReceipt`. Use **Reload
source** after production edits; ES modules are cached within a page session.

Existing fixture directories are never overwritten. If a prior fixture or its
receipts are present, preserve them and prepare a named sibling:

```sh
node scripts/prepare-fpv-environment-verification.mjs --out dist/fpv-environment-verification-review
```

Open the corresponding printed URL. The checked-in HTML under `docs/evidence`
uses the default prepared directory; each generated copy uses its own sibling
`before` directory and manifest. The preparation script can be run while an older
fixture is open because a different output name leaves that fixture untouched.

## Workload and meaning

The two actual renderers use identical snapshots generated by ordinary fixed-step
commands from the frozen flight model. V1 Academy commands contain four axes;
World v2 also supplies action bits. The selected authored courses jointly cover
drone, hazard, patrol, sentry and vehicle actors. Gameplay course bytes must match
between current and baseline catalogues.

The run covers eight worlds × three presets × FPV/chase/overview × three rounds
× two renderers: **432 renderer configurations**. Six worlds load actual builtin
GLBs; receipts retain their hashes, byte sizes, mesh/node counts and GPU-instancing
metadata. Each view receives warmup draws and six measured draws. Measured order
alternates by round. Both canvases have fixed 640 × 360 CSS dimensions and the
browser's recorded DPR. Additional checks cover all eight procedural fallbacks,
snapshot immutability, repeated scene resource plateaus, disposal, source hashes
before/after, WebGL errors, context loss and console errors.

The preview controls render matching before/after views and can disable imported
scenery to inspect fallbacks. They support human visual review but do not
constitute automated aesthetic or collision acceptance.

`submitMs` measures synchronous `renderer.draw` scripting/driver submission;
`rafCadenceMs` includes browser scheduling and nearby work. Neither reports GPU
execution time, sustained fps, physical controller latency or target-hardware
qualification. Calls/triangles describe the last render; resource counters are
object counts, not measured VRAM. Three rounds and small per-view samples are a
functional regression workload, not a statistically controlled hardware benchmark.

Only a completed receipt with `passed: true` confirms these checks. Preparing the
fixture, parsing scripts or fetching modules successfully does not establish a
browser pass. Named desktop/mobile/Steam Deck sustained measurements and player
readability acceptance remain separate qualification work.
