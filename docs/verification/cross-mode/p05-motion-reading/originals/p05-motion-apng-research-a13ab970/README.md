# APNG default-image discrepancy — research recommendation

**The red APNG default-image expectation is supported; a blue result is consistent with a known browser decoder distinction.** Keep the Motion candidate unaccepted for this specific poster-identity contract until the parent’s comparable native observations are retained. A stable blue image is not evidence that the background animates.

## What is established

The current Canvas rule selects the format’s default image for disabled animation, using the first animation frame only if no default exists. [WHATWG Canvas](https://html.spec.whatwg.org/multipage/canvas.html#image-sources-for-2d-rendering-contexts). PNG3 defines the IDAT static image separately when the first fcTL comes after it. [PNG3 APNG structure](https://www.w3.org/TR/png-3/#4Concepts.APNG).

Both fixture PNGs have valid complete chunk framing and CRCs. The APNG sequence is IHDR → acTL → IDAT → fcTL/fdAT → fcTL/fdAT → IEND. Its 65-byte compressed IDAT is byte-identical to `static-default.png` (SHA-256 `382ca8c711fd4c95504ad57ac946cf5d99a6c7c501606d6ed8b8f4ef49d5e6cc`). The retained fixture manifest identifies that default as red and first animation frame as blue. This read-only check does not depend on screenshot color inference.

Historical Chromium and Mozilla implementation discussions explicitly describe skipping the hidden fallback/poster frame and returning the first visible animation frame to canvas. That is a close match for the parent-reported blue APNG. [Chromium discussion, comment 28](https://codereview.chromium.org/1250373006/#msg28), [Mozilla decoder discussion, comment 1](https://bugzilla.mozilla.org/show_bug.cgi?id=1187546#c1). Current upstream Chromium’s `Ihdr50ActlIdatFctl30Fdat` decoder test also distinguishes static IDAT from decoder frame zero’s first animated fdAT; it does not establish a canvas result on the actual device. [Chromium decoder test](https://chromium.googlesource.com/chromium/src/+/HEAD/third_party/blink/renderer/platform/image-decoders/png/png_image_decoder_test.cc).

Motion currently hands the unmodified File to an object URL and an HTMLImageElement (app.js 712–764), then calls drawImage on that element for each render (1249–1260). No game code explicitly selects the blue frame. Preserve the native browser/version, file hash, same palette/fit/opacity and Play/redraw observations separately. Do not relabel the original red conformance expectation as passed merely because the browser behavior is historically explained.

## Narrow recommended correction — not implemented

Use a **PNG-only static-preview derivative**, leaving the original File bytes intact. This needs no custom image codec, pixel decoder, canvas re-encoding, worker, ImageBitmap lifecycle or change to GIF/JPEG/WebP handling.

1. Keep the existing 25 MiB encoded-file acceptance limit and enforce it again before reading a PNG ArrayBuffer. Validate signature, complete chunk framing and unsigned lengths against the remaining buffer; bound chunk count and derived output size. Validate CRCs for chunks being relied on or copied. Require one leading IHDR, valid dimensions/PNG header fields, a valid contiguous IDAT run and terminating zero-length IEND with no truncated trailing material. Reject malformed structure visibly while retaining the accepted background. Do not decompress IDAT in application code.
2. For a valid APNG, omit only acTL, fcTL and fdAT from an in-memory derivative; preserve the signature and all ordinary PNG chunks, order, compressed IDAT and existing CRC bytes. Native PNG decoding still validates the resulting image. Removing animation chunks exposes exactly the original IDAT fallback/default; no new pixel rendering interpretation is invented. A normal valid static PNG can retain its original Blob path. Do not serve or save the derivative as a replacement source asset.
3. Record a clear local-preview status that an animation input uses a still preview. Keep original file identity/dimensions visible and ordinary errors recoverable. A parser failure must not silently fall back to the known wrong-frame APNG path and claim the contract passed.
4. Claim the upload generation and busy status **before** the new asynchronous byte read. Clear, a newer upload, pagehide and terminal disposal invalidate that generation. After every await, verify ownership before creating an object URL, assigning pending state, setting src or changing status. A stale byte-read completion must do nothing; any stale created URL must be revoked. Preserve the old accepted image until the replacement’s real load succeeds. Keep existing Clear/failed-decode semantics and URL retirement.
5. This bounds preparation by encoded bytes and chunk count. It does **not** establish a native decoded-pixel/memory budget: the existing importer lacks one. Do not call the preparation bound a full decoder resource limit. If a pixel cap is added, give it an explicit product limit and separate acceptance; it is not required to explain the APNG frame mismatch.

The existing parser can be a small pure helper, isolated from DOM/lifecycle. Retain original CRCs; there is no need for a new encoder. Apply this as a new successor patch after the frozen two candidates, preserving their original native failure/evidence.

## Minimal discriminating checks

- **Pure fixture check:** the separated-default APNG derivative equals the static control bytes for this supplied minimal fixture; default-as-first APNG still retains its complete IDAT image; a multi-IDAT stream retains exact bytes/order. Static PNG, non-PNG formats and original uploaded byte arrays remain unchanged.
- **Parser failure checks:** truncated header/chunk/CRC, length beyond buffer, invalid CRC, missing/duplicate IHDR or IEND, absent/noncontiguous IDAT, excessive chunk count, over-limit input/output. These must reject without partial successful output. Include metadata/color/transparency chunks to prevent a naive critical-chunks-only filter from altering appearance.
- **Composed host checks:** pending byte read A superseded by B, Clear before resolution, departure/disposal and failed preparation all retain old background or cleared state as authored, never resurrect stale URL/status/focus. Successful native Image load remains the commit point. Run the complete affected host and pure-helper files on the existing two Node families; do not count overlapping cases as new qualification.
- **Actual native check:** root reuses exactly this APNG and the static control at identical settings; accepted APNG must now show red across Play, Pause, explicit redraw and reduced effects. Retest actual invalid replacement and Clear, plus the already-observed GIF/WebP controls. Browser history admission and natural pending-decode race observations stay separate.

## Alternatives and limits

Simply switching to `createImageBitmap` is not a demonstrated repair: the specification has the same default-image rule, and engines may use the same underlying decoder. [WHATWG ImageBitmap](https://html.spec.whatwg.org/multipage/imagebitmap-and-animations.html#dom-createimagebitmap). Snapshotting the first draw would freeze the already wrong blue frame. Renaming APNG to PNG or changing only MIME does not remove its animation chunks. Rejecting APNG is smaller operationally but withdraws supported input; loosening the product promise to whichever frame the browser supplies abandons exact artwork identity. Prefer the narrow deterministic derivative when the preserved default remains the intended contract.

No browser, production/candidate/fixture mutation, image derivative, test, build or deployment was performed here. `review.json` pins the exact candidate and fixture bytes. `sources.json` distinguishes current specifications, historical implementer explanations and current upstream tests; attempted unavailable current WPT/implementation URLs are explicitly not evidence. Parent-owned screenshots and native outcome remain the acceptance authority.
