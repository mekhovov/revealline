## History-restored Settings fields

The next review reproduced stale form values after browser history restoration even when the authoritative preferences were unchanged. All three mounted hosts failed the initial regression. Settings now repaints palette, ornaments, text style/size, Reduced effects and master volume from the current preference owners immediately after `pageshow` and in one guarded later task. The later task reads current intent again, preserves failed-save warnings, and is cancelled on departure. It never adopts or saves browser-restored values. Team uses pure field rendering here; an ordinary explicit appearance change retains its separate focus-clearance behavior.

This timing check follows the documented history traversal order: form state can be restored after `pageshow`, so an immediate callback alone is insufficient. See [MDN's history-event sequence](https://developer.mozilla.org/en-US/docs/Web/API/Window/popstate_event). Browser guidance also recommends reconciling stale application data after a cached-page return; see [web.dev's BFCache guidance](https://web.dev/articles/bfcache#update_stale_or_sensitive_data_after_bfcache_restore). Neither reference proves this candidate's native browser admission.
