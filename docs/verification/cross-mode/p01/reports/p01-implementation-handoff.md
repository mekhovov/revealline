## Recommended seam

Use a small **scoped operation-status presenter** shared by DOM hosts. Proposed new files: `game/ui/operation-status.mjs` and `game/ui/operation-status.css`. The presenter renders the operation already owned by a screen; it must not become a second content, save, image or playback coordinator.

The best existing patterns are `optional-chapters-panel.mjs: run()/cancelPending()` and `still-media-panel.mjs: work()`: status before work, an explicit operation owner, a usable escape action, stale-completion fences and deliberate return focus. Solo's concrete fan-out seam is `app.mjs: contentStatus()` plus the launch/picture/restore callbacks in `game-shell.mjs`; retain those adapters. `presentation/page.mjs` is a useful asset-readiness publisher, but only owns cosmetic presentation. `ui/event-feedback.mjs` owns gameplay animation and is not the asynchronous operation seam.

Agree a small interface before parallel changes:

- The host supplies a target status node, operation identity/current-owner predicate, stage/message, optional measured progress and explicit actions. It controls which work conflicts. The presenter can fence its own DOM lease but cannot adopt a flight, clear a storage lock or decide that a write was rolled back.
- Announce a meaningful label synchronously before the first await or dynamic import. Use a compact pixel signal and real text, existing typography/tokens, and a static reduced-motion state. Boot additionally needs inline/static feedback independent of the delayed script and font files. Do not introduce a synthetic percentage, minimum loading delay or new asset dependency just to show loading.
- Separate preparing/downloading/verifying/saving from ready, failed, cancelled and **still running after observation ended**. Render numeric progress only with a real denominator and clear units. Asset decode without a denominator remains indeterminate. Throttle repetitive live-region announcements; keep the status outside a subtree whose `aria-busy` suppresses its announcements.
- Keep Cancel/Back reachable by current keyboard/controller routing and touch. Host-provided actions distinguish aborting interruptible work, abandoning an uncommitted candidate, and merely stopping observation. A durable commit or shared worker may continue. Do not inert an entire dialog including its escape action.
- Keep initial disabled states and focus intent; restore them only for the same live operation. A stale `finally` must not enable controls held by a newer operation. Closing/reopening, a changed selection/run, page disposal or blur must fence both status and focus effects. Do not move focus simply because an image or promise completes.
- Foreground Deploy/Continue can observe an existing picture-prewarm promise; never start a second download/decode. Cosmetic body or decoration loading does not block a playable run. Required-picture failure remains visible and retriable without falsely approving a fallback; P04/P06/P08-A own the complete binding policy.

In Solo, preserve the exact `resume()` checks for ticket/generation, picture owner, selected run/theme, visibility, document focus, open dialogs and course state. Preserve audio activation on the original gesture before awaiting, explicit Resume after restore, input clearing and neutral-input gates. P01 is not authority to auto-resume after closing a loading dialog.

## Highest-risk finding: offline preparation outlives its UI timeout

Existing public evidence, performed by the release owner rather than this review: Archive 13 v0.54.0, source `1af33851e93ee95110de20cc73622ed43d85a4da`, deployment 6453754021, workflow 34941045432. At `https://mekhovov.github.io/revealline-archive-13/releases/v0.54.0/site/game/`, the first preparation exceeded the existing 60-second UI wait while the worker continued. Ordinary retry then verified **600 files / 55,099,084 bytes**, with no missing or corrupt files; offline reload/play passed. Evidence is retained in `publishing/pages-controller/evidence/archive-13/browser-review.json` and its referenced timeout/preparing/ready observations. This is desktop automated Chromium evidence, not a physical-device or new-process offline cold-start claim.

The same source mechanism remains in integrated main:

1. `game/offline.mjs: installed()` removes its state listener and rejects after 60,000 ms. It does not stop the service worker or its network work.
2. `prepareOffline()` waits for that function before sending `revealline.offline-prepare`. `requestReport()` then has a separate 30,000 ms timeout and accepts the first port message as its terminal reply. Adding a spinner or extending that latter timeout cannot observe the initial download.
3. `app.mjs: offline-button.onclick` catches the timeout, re-enables Prepare and leaves `offlinePrepared` false. There is no screen-generation/cancellation owner around its status callback. A later retry can find the installed/waiting worker and successfully verify.
4. `offline/service-worker.template.js` intentionally shares one `installation` promise between clients, verifies every body before cache creation, writes the ready marker last and does not call `skipWaiting`. It currently sends terminal reports only. Its four-download concurrency, 64 MiB inventory budget, 2,000-file limit, integrity checks and cache admission must remain intact.

**P01 correction:** observe the exact scoped/build-bound installation while it is installing, expose actual stage/progress, and distinguish observation timeout from installation failure. Offer truthful “still preparing / check progress” recovery. Closing the screen or Stop waiting detaches that caller; it must not unregister a worker, delete caches or cancel another tab's shared installation. Reopening/retrying rejoins existing work and verifies its actual state. An actual redundant worker, download/integrity/storage error remains a failure. A ready report for another scope/build is never adopted. A waiting update keeps the close-tabs instruction and current game intact.

If worker progress is added, use a versioned request/reply envelope or separate message type, with operation/request ID, build identity, explicit progress versus terminal replies and bounded subscriber cleanup. Preserve the old terminal-only protocol: its current consumer would otherwise treat the first progress message as completion. Observe during the install wait, not only after `installed()`. Do not patch historical frozen workers. A compatibility fallback must remain truthful when only old terminal reports are supported. Count downloaded/verified/saved work separately; ready still means all required bytes and the ready marker have passed verification.

Required focused fixtures: slow successful install beyond 60 seconds; separate report timeout; close/reopen while installing; retry and two tabs sharing one install; changed build/worker; stale completion after a newer request; cancelled observation with successful durable completion; missing/corrupt bytes and quota failure; interrupted cached verification; waiting update; cached immediate success. Retain the first timeout and later success as separate observations in evidence.
