# P01 craft preparation inside Missions

The [public v0.57.1 interface review](loading-placement/public-interface/review.json) found that Flight setup starts real craft loading, but its `craft-preparation-status` belongs to the background arena. At 1280×800, native preparation showed “Loading craft and scene artwork…” at y777.48–797.78 while the top-layer Missions dialog covered it. Hit testing reached the deploy bar. The owned page was visible and focused; this observation is separate from the earlier excluded hidden-page attempt. Preparation reached ready without a data error.

The correction moves the same status element into a full-width row inside the existing sticky Missions heading. It covers normal mission selection and direct briefing, without depending on the hidden mission-content or deploy-bar regions. An empty/ready row collapses; errors remain readable. Actual close and disposal restore the original position; a queued old close leaves the current modal's status intact. The host presenter, renderer's load-token guards, focus, flight state and nonblocking cosmetic policy remain unchanged.

The first focused actual-host navigation/renderer batch passed 59 tests, including two new placement/lifecycle cases. Existing delayed image and stale renderer completion tests remain unchanged. The first native correction trial then exposed an overlap at both 390×844 and 844×390 with Large/Plain/Reduced text: the separate sticky status and existing sticky heading both used top zero, and the heading covered the loading label. The first enabled setup selector remained unobstructed. These were actual transient status/hit-test observations; no painted busy frame is claimed.

The revised layout puts heading and feedback in one sticky box instead of competing layers. Its native review confirmed the label and Back action in all four Standard/Large portrait/landscape cells, but exposed another problem: the expanded heading covered the top of the focused Pack selector in Large portrait, and the bottom action bar covered its lower edge in Large landscape. Bounds inside the viewport alone had not detected either overlap. That failed trial is retained in the [evidence index](loading-placement/copies.json).

The final correction measures the heading's lower edge and the action bar's upper edge. `attachFocusClearance` adjusts scrolling only enough to expose the current enabled control between them, without moving focus or reacting to ordinary wheel/touch scrolling. It reads current focus when the scheduled layout callback runs, ignores hidden/closed/disposed hosts, and keeps a tall control's beginning visible. Both Missions entry paths use the same helper.

Nine recorded-geometry cases and the existing actual-host navigation/renderer tests pass together: 68 tests, zero failures. An independent source review found no concrete blocker. These tests establish ownership and geometry behavior, not painted-browser visibility.

The [final native correction review](loading-placement/craft-final/run/review.md) passes all four Standard/Large portrait/landscape cells. The focused Pack selector, loading label and Back each pass center and four interior hit tests. Large landscape and portrait screenshots paint the actual loading state; Standard preparation finished before its later captures. Direct briefing shows real loading in portrait and the collapsed ready state in landscape. All 227 foreground guards passed, and 16 runtime/source pins remained unchanged through browser closure. The original filenames and failed/inconclusive attempts are preserved.

The browser's later animation-frame and timer callbacks were delayed despite visible/focused guards; craft preparation eventually cleared. The report retains that timing uncertainty and the full 250-entry resource buffer's limits, without attributing a cause or changing runtime timing. These observations do not establish physical-device or performance qualification.
