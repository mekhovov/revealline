retains original hashes, screenshots, failures and those boundaries.

1. In a backed-up disposable test profile, remove exactly one named dependency
   from one owned prepared cache using browser storage inspection. Record its
   original hash, exact cache and URL; do not delete a whole origin.
2. Ask the launcher to check readiness. Repeat in a separate setup with only the
   owning worker unregistered while cached files remain. A saved pointer/icon is
   insufficient in either case. Keep other apps installed as isolation witnesses.
3. Exercise the offered repair/re-download. Simulate an inconclusive check
   separately: unknown/timeout must not be presented as verified readiness or
   confirmed corruption. Preserve the last actually verified version as designed.
4. Remove one app's offline copy through its UI. Confirm that action preserves
   app records/imported worlds and the other two apps' scopes, cached readiness
   and data. Distinguish app-shell removal from OS icon uninstall and deliberate
   record/content deletion. Repeat with each app as the removed target.

**Expected:** missing dependencies/ownership prevent a false Ready claim; recovery
is actionable and scoped; the unchanged siblings still work offline. Any data
loss is release-blocking and must be captured before further repair attempts.

### C8 — Same-device packaged performance and repeated recovery

1. Record device/CPU/GPU/OS/browser, power state, display/viewport/DPR, app/mode,
   quality, input, exact package and representative scene/content hashes.
2. Agree the relevant SIM performance thresholds and workload **before** measuring.
   Use comparable old/current candidates on that same setup where a regression
   claim is intended. Include moving flight, ordinary menus and repeated scene
   loading/unloading; retain cold and warm observations separately.
3. Collect elapsed duration, frame/callback samples, CPU submission separately
   from GPU measurements, exposed ownership counters, disposal behavior, errors
   and outliers. Record other active contexts/workloads. A stationary callback
   sample or simulated 7,200 seconds is not elapsed moving-play evidence.
4. Repeat Tropical preparation under controlled ordinary context load. Retain
   H7's timeout and successful retry separately; determine whether the current
   candidate reports graphics preparation failure honestly and recovers without
   mutating saved content or implicitly arming.

**Expected:** actual accepted thresholds are met or a failure is recorded. No
inferred GPU/FPS number, unmeasured memory claim, broader-device extrapolation or
deadline increase solely to turn a failure green.

### C9 — Physical inputs, assistive behavior and native zoom

1. Use named physical keyboard/controller/radio and touch-device setups matching
   each package's advertised support. Calibrate through normal UI; record hardware,
   connection, mapping, firmware where relevant and tested operating mode.
2. Navigate directory, launcher, setup, flight, pause/retry and back. Disconnect
   and reconnect during flight/setup; verify explicit safe pickup and neutral
   input rules, not automatic resumed motion. Record which app/input combinations
   were actually tested; emulator events cannot stand in for the hardware.
3. At actual browser 200% zoom and narrow/short orientation, verify readable text,
   visible focus, reachable controls and no obscured modal exit. Test reduced
   motion in the full shell, not only the component fixture.
4. With a named screen reader, listen to loading/progress/failure/readiness and
   retry announcements in EN/UK; check control names and modal focus. Capture
   observations without private credentials or personal content.

**Expected:** supported routes are usable and safe on the stated setup; no claim
that a DOM `aria-live` attribute proves announcements. Unavailable devices remain
explicit gaps for the release owner, not reasons to halt unrelated implementation.

### C10 — Player/maintainer guide and real learning walkthrough

1. A real participant starts with only the directory and EN/UK player guide.
   Record prior experience and chosen app/task. Observe app choice, input setup,
   existing demonstration/first flight, pause/retry and one beginner exercise.
2. Ask the participant to explain the next action and why it is needed. Record
   confusion, assistance, retries, elapsed task time and the actual outcome.
   Review pacing and comprehension; replayed completion or a scripted proof is
   not evidence that a person learned the skill.
3. Follow offline preparation, home-screen installation, update, removal and
   backup instructions on the current candidate. Verify `.rlpack` means World
   content, not a new executable directory app. Capture current screenshots.
4. Separately have a maintainer follow the existing fourth-sample recipe from
   scratch; record any undocumented step. H11's automated lifecycle is already
   useful regression evidence and need not be invented again as human review.

**Expected:** guides describe the actual UI and distinguish Play/offline/icon
installation. The actual reviewer decides learning/pacing acceptance and records
participant coverage; this checklist neither chooses a fictitious reviewer nor
sets an invented universal participant count.

### C11 — Content/asset review and evidence packaging

1. Review actual package descriptions, requirements, guide translations,
   thumbnails and app content against the frozen inventory. Verify vendor and
   asset license/attribution/source records, including any remote content pin
   relevant to the tested journey; do not assume a screenshot grants reuse rights.
2. Gather original receipts/screenshots, preserve every failed attempt, and
   calculate exact byte lengths and SHA-256 values. Remove secrets/private
   participant data only through an explicit redacted derivative; keep its
   relationship to the privately retained original clear.
3. Prepare each package's eight real review entries using existing schema and
   public evidence naming. The designated reviewer signs only supported claims.
4. Run existing `publish-optional-packages.mjs verify --bundle … --review …`.
   Keep upload, release allocation, selector changes and hosting work deferred.

**Expected:** complete, attributable, approved evidence; verification rejects any
pending gate, wrong envelope, missing/changed evidence or invented approval.

## Required receipt fields for every case

- Case ID and package ID; status `passed`, `failed`, `blocked` or `not run`;
  actual operator/reviewer and timestamp, not placeholders recorded as people.
- Source commit/tree; candidate/envelope/manifest/archive hashes; app revision,
  version, stable root; previous candidate identity when testing migration.
- Browser build, OS/device/input, viewport/zoom/DPR, network conditions, content
  pins, settings, profile isolation and whether a new process was actually used.
- Exact public actions, expected result, observed result, fresh status transitions,
  request/fault timing and reproduction controls. Label injected versus natural
  failures and simulated versus elapsed time.
- Before/after export and data identities, screenshots/logs with lengths/hashes,
  complete failure history, cleanup/resource results and explicit limitations.
- Gate(s) supported, evidence-storage location, publication/redaction approval
  and any reason evidence is inapplicable to a later candidate.

## Recommended next order (hosting remains deferred)

1. **P0: C1–C7 on the frozen real three-app candidate.** These establish executable
   completeness, honest offline readiness and data preservation. Missing this
   proof risks stranded installations or lost work; it is more important than
   catalogue polish. Run the observer lane and first-pointer/manual lane in
   parallel, preserving the boundary between them.
2. **P1, still subject to required gates: C8–C10 on available named setups.** These
   establish actual playability and understandable instructions. Otherwise a
   technically valid package can remain unusable or unlearnable. Record missing
   physical/human resources explicitly; do not claim their gates passed.
3. **C11: assemble actual review evidence when each prerequisite exists.** Package
   review can progress independently of hosting, but publication eligibility
   requires all ordinary gate decisions. No test harness may invent approval.
4. **Deferred: capacity, hosting choice, release allocation/upload/selection and
   public end-to-end verification.** Preserve their requirements in the main
   plan; do not reopen the architectural decision inside this checklist or label
   the public release complete while they are deferred.
