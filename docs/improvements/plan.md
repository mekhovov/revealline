The game already provides substantial functionality: detailed mission rules, achievement requirements, safe-area handling, touch cancellation, reduced motion, audio-resume paths, verified downloads, repair, writer protection and migration safeguards. Improvements should extend these systems.

### Priority and estimate conventions

- **P1:** correctness, progress protection, access and significant first-session friction.
- **P2:** learning, comfort, replayability, creation and community participation.
- **P3:** optional expansion or larger operational investment.
- **Impact:** expected **player/game** benefit, using **H**igh or **M**edium. These are prioritization judgments, not measured retention results.
- **Effort:** developer working days including focused verification. Hardware waiting, review queues, external accounts, substantial asset production and ongoing curation are excluded.
- Phase numbers group outcomes. **Independent P1 work can begin across phases simultaneously.**

Research informs the approach: contextual teaching from [Factorio](https://www.factorio.com/blog/post/fff-361), interruption-friendly progression from [Returnal](https://blog.playstation.com/2021/10/26/returnal-2-0-update-brings-suspend-cycle-and-photo-mode/), configurable presentation and redundant cues from the [Xbox Accessibility Guidelines](https://learn.microsoft.com/en-us/xbox/accessibility/guidelines), and complete focus behavior from [W3C dialog guidance](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). These patterns require validation in this game.

## 2. Delivery model and complete PR phases

### Phase 0 — Establish a safe implementation baseline

**SETUP · 0.5–1.5 days**

Record the current base, preserved local changes, existing fixes and ownership. Before implementation, compare the audit findings with current `main` and reproduce relevant failures on the intended candidate.

Create the feature/PR tracker and identify the existing shared-demo work as an explicit predecessor, called **D** below. A finding fixed upstream becomes **Superseded with evidence**; it does not generate an unnecessary PR.

Use one isolated branch/worktree per PR, with at most **three implementation PRs active** and one integration owner. Assign shared menus, localization registries, generated assets and common styles to a coordinated owner.

Each PR must deliver a complete usable slice: behavior, UI, English/Ukrainian copy, persistence, failure handling and relevant verification. Assessment PRs deliver evidence and a bounded specification; they do not count as shipped features.

Keep review candidates as drafts. Repository automation can merge eligible non-draft PRs and publish changes, so draft promotion and release readiness must remain deliberate.

### Core acceptance scenarios

- **Navigation:** pointer, keyboard and available controller paths; nested Back; opener focus; no underlying game resume.

- **Gameplay:** complete representative attempts, deterministic checks where relevant, and correct reward/record classification.
