The intended repair is a new v0.17.1 source/build with the normal service-worker lifecycle, not a diagnostic worker shipped as a release. The pre-change baseline is `.cache/round-27-1/integrity/frozen-releases-before-v0171.json` (SHA-256 `3b704d3a8e148b1b366c4ea06ac41eef8db392e6a233c2d848499068f664e86a`); it preserves 21 release trees and 22 tags. Acceptance of this plan does not establish that the implementation or browser checks have passed.

## Evidence and uncertainty

Frozen v0.17.0's ordinary installation repeatedly became redundant despite all 135 served file hashes passing external HTTP checks. The [first diagnostic](../.cache/round-27/offline-diagnostic/public-prepare-result.txt) moved the original installation routine into the existing public Prepare-message path and exposed a Cache.put network error. The [second diagnostic](../.cache/round-27/offline-diagnostic-write-stage/public-prepare-result.txt) identified `game/content/packs/equipment-workshop.json` after all downloads had passed byte verification. Closing five completed QA tabs did not prevent the failure.

The [third diagnostic](../.cache/round-27/offline-diagnostic-owned-bytes/public-prepare-result.txt) consumed each original body, verified its bytes and retained a synthetic Response over those bytes. It reported **135 files / 31,764,790 bytes verified**, build `9c9ead88556353f1cf1b97b737ef033eacb8e32a9807524300ce0898622fd4b2`. That copy still bypassed ordinary installation/activation readiness, so it supports this ownership strategy but does not prove production readiness or the frozen lifecycle fixed.

The underlying Chromium/network-body/storage failure is **not diagnosed** as quota, disk spooling, memory exhaustion or corrupt artwork. Response cloning tees a body stream, which makes retaining unread originals while consuming their clones a plausible failure boundary; that is an inference, not a measured browser internals result. [Fetch body cloning](https://fetch.spec.whatwg.org/#concept-body-clone), [Streams teeing](https://streams.spec.whatwg.org/#rs-tee).

## Scope and ownership

Production changes are limited to [service-worker.template.js](../game/offline/service-worker.template.js) and meaningful regressions in [offline.test.mjs](../game/test/offline.test.mjs). Root owns the v0.17.1 metadata, builds, browser tests, freeze and evidence. No game UI, profile, pack, image, core, replay or save format changes. Source pages still register no worker automatically; preparation remains an explicit user action. Keep the current `revealline-offline.v1` configuration/report contract and origin/path-derived cache keys.

A private network-body helper shared by **installation** and **missing-file network repair** returns owned verified bytes and response metadata. Do not change cached `verified()` or `inspect()` behavior. Do not copy lifecycle bypasses or diagnostic prefixes from the probes into production.

## Owned, bounded network body

Use a helper conceptually named `downloadVerified(url, file)` returning `{ bytes, status, statusText, headers }`; the URL remains the known same-scope manifest/cache key. It performs the existing fetch with `cache: 'reload'` and `credentials: 'same-origin'`.

1. Before allocating a body buffer, require `file.bytes` to be a nonnegative safe integer within the existing **64 MiB total inventory budget**. Check that the generated inventory contains at most **2,000 files** and its finite sum remains within that same budget. These are runtime guards for existing build limits, not raised limits or a new configurable quota. Do not size storage from Content-Length.
2. Retain the existing same-scope URL, redirected-response, successful-status and opaque/error rejection. Reject partial status 206 and `Vary: *` before retaining bytes, because these cannot form the existing complete Cache.put entry. Preserve ordinary Vary values. Rejected responses never create a cache/ready marker.
3. Consume the **original** body through its reader, without cloning the network Response. Allocate exactly `file.bytes` once. For each byte chunk, check its length against the remaining budget **before copying** into the buffer; cancel the reader on overrun or read failure, release its lock in `finally`, and reject. Do not allocate a second concatenation buffer or keep an unbounded chunk list. A browser-provided chunk can itself exceed the budget; reject it without copying, rather than claiming to control the browser's internal allocation.
4. Require end-of-stream exactly at `file.bytes`; reject truncated/errored bodies and mismatched SHA-256. A missing body is acceptable only for an expected empty file with the matching empty hash; otherwise reject. The existing manifest SHA-256 describes the bytes delivered to the application. Never accept a valid declared size alone.
5. Retain only the owned Uint8Array and an owned copy of response metadata, then release the original Response/reader references. Construct synthetic Responses only when writing or returning them. Preserve valid status/statusText, including an empty statusText. For supported empty 204/205 responses, construct with a null body; nonempty null-body statuses are invalid. The actual distribution uses normal 200 responses, but the helper should not accidentally reject an otherwise valid zero-byte response merely because Response forbids a body for that status.

The manifest budget bounds retained application payload bytes; it does not certify a maximum browser heap. SHA-256, Response construction, Cache.put and the browser's own streams may temporarily copy a body. During installation, clear each retained byte reference after its cache write resolves so already-written application buffers need not remain live until the last file. Keep serial reads/writes rather than introducing parallel network buffering.

## Header policy for verified decoded bytes

Fetch's HTTP-network algorithm handles content codings before exposing body bytes and explicitly notes that this can make the original Content-Length unreliable. Response construction uses the supplied body; it does not recreate the original network encoding. This repair therefore hashes/owns the delivered bytes, then gives its reconstructed Response metadata consistent with those bytes. [Fetch HTTP-network algorithm](https://fetch.spec.whatwg.org/#http-network-fetch), [Response construction](https://fetch.spec.whatwg.org/#dom-response).

Copy exposed headers into `new Headers(response.headers)`, **delete Content-Encoding**, and **set Content-Length to the verified byte count**. Retain Content-Type, Content-Security-Policy and other security headers, Cache-Control, Vary, validators and all other exposed headers without an unrelated allowlist rewrite. Do not recompress, change image bytes or trust a compressed Content-Length as an allocation bound. Unsupported/incorrect coding that leaves bytes different from the manifest fails the hash before reconstruction; deletion of a header must never make unverified content acceptable.

The new Response has a synthetic URL/type; preserve the request/cache URL explicitly, not by trying to assign read-only Response properties. Same-scope nonredirected resources and normal navigation/module/relative-asset browser checks remain required. Ordinary Vary cache matching must continue to work; do not use `ignoreVary` to hide an entry mismatch. The service-worker Cache.put algorithm consumes the body and rejects incompatible partial/Vary entries. [Cache.put specification](https://w3c.github.io/ServiceWorker/#cache-put).

## Installation and repair invariants

**Installation:** reuse an already ready cache exactly as today. Otherwise fetch, own and verify **every file before opening a new build cache**. Only then construct one synthetic Response per retained record and write entries serially. Write `.offline-ready` last, after all content writes succeed. Any cache write or marker failure deletes only this candidate build's partial cache and rejects installation. Download/hash/read errors before cache creation leave the older cache untouched.

The normal install listener still waits for `install()`. The activation handler still requires `inspect().status === 'ready'` before it may clean other builds under the exact same scope prefix and claim clients. This handler guard is not a browser rollback guarantee: rejecting activation's waitUntil does not promise to restore the previous active worker. The all-files-before-install-resolution guarantee remains essential. [Service Worker activation algorithm](https://w3c.github.io/ServiceWorker/#activation-algorithm). **No `skipWaiting`, activation bypass, eager cache deletion, altered scope, fabricated marker or automatic integrity disable.** Existing waiting-worker behavior stays intact. Keep older builds and other application/release scopes byte-identical while the new download/write is pending or fails.

**Missing-file repair:** retain current GET/known-file/same-scope routing, navigation normalization and cached-hit behavior. On a miss, use the same bounded helper and header policy. Create separate synthetic Responses from the verified owned bytes for Cache.put and the caller, so consuming one cannot consume the other; there is no retained network clone. Return success only after the cache write resolves, as today. On fetch/read/hash/constructor/write failure return the existing 503 recovery text, without altering unrelated cached entries or the ready marker. Do not expand this change into automatically repairing corrupt cached hits; existing `inspect()` and explicit Prepare remain that path.

## Meaningful tests

Extend the existing worker VM harness with real `Response`, `Headers` and byte `ReadableStream` objects and injectable network/cache failures. Its current fake Cache.put clones without consuming; make the new-path tests actually consume supplied response bodies before storing their own cache copy. Preserve old tests and old fixtures; do not claim a Node mock reproduces Chromium's precise NetworkError.

- A real chunked body reaches the cache and caller with exact bytes, status and headers; the fetched Response is consumed without its `clone()` being invoked. Both install and repair use this ownership boundary, and cached self-check remains no-network.
- Stream exact-length success, overrun within a chunk, extra trailing chunk, premature EOF, stream rejection, null positive-length body and valid empty body exercise cancellation/release and zero cache/marker writes on invalid input. Invalid/overbudget expected sizes reject before application buffer allocation/body reading. Bad SHA, redirect, opaque/error, unsuccessful status, 206 and `Vary: *` remain failures.
- Real Workshop JSON transport uses the actual 11,127,024-byte source file and its existing SHA-256. Reconstructed cached bytes must match it exactly; no generated art or route fixtures change. Include it in both ordinary install and missing-file repair, without multiplying large copies across unrelated tests.
- Test delivered decoded payloads with gzip and br header variants: verified decoded bytes survive, Content-Encoding is absent, Content-Length is the verified decoded length, and Content-Type/CSP/cache/Vary/status remain correct. A local Node HTTP fixture may gzip/brotli actual bytes and use native fetch to demonstrate decompression; a manually constructed Response with those headers alone tests header policy, **not decompression**. Report these scopes separately. Do not introduce a runtime compression dependency.
- A deferred final download must leave a prior build intact and the new cache absent. A later hash failure still leaves it intact. Asset-put and ready-marker-put failures remove only the partial new build. Successful installation writes the marker last; activation removes only previous builds in this exact scope and never skips waiting. Snapshot the old entry bytes, not just cache names.
- A repair write failure returns 503 and preserves unrelated entries. Valid repair returns a readable independent response with exact hash and can subsequently be read offline. Existing unknown-route/method/other-scope behavior remains unchanged.

Tests should prove these authority/resource boundaries rather than mirror implementation strings or simply count API calls. Use focused tests/lint/format first, then the accepted final source gates after integration; keep the earlier 1,550-test and six-case gallery follow-up evidence separate.

Preserve v0.17.0 as the release where this installation failure was found; do not overwrite its files, worker or reports. A probe success is not substituted for these normal install/activate and archived-build checks.

Done means the new build prepares with normal lifecycle enforcement, retains verified owned content through installation and repair, survives the recorded offline journeys and preserves older versions. It does not claim that the underlying browser defect, quota behavior on every device, public hosting or physical hardware has been certified.
