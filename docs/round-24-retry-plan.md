# Round 24 — clear reasons for Retry

Implementation contract accepted after parent and independent review on 12 September 2026, against tagged source `c7b0122edffcaabbdfa6a817c06f603625f79fe0` for v0.13.0. That release archive remains frozen; implementation follows separately. This document changes no historical source or evidence. It refines [the candidate backlog](round-24-candidate-backlog.md) into one small solo-game improvement: explain the actual ended attempt and give one useful next step beside the existing Retry action.

**Preserve immediate Retry:** one explicit activation of Retry calls the existing `prepare()` then `resume()` and starts one fresh running attempt. Merely losing, reading the explanation, leaving a reader, waiting or receiving a controller status update must not restart. There is no added confirmation, countdown, tutorial, reward, difficulty adjustment or rule change. This resolves the backlog's ambiguous phrase “no automatic relaunch”; it does not mean that Retry should stop at another Ready screen.

## Existing authority and presentation

| Existing path                                                            | Relevant fact                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Core `createRun`/`recover`/`complete`](../game/core/index.mjs)          | A fresh run starts with `failureCause:null`. Recovery sets the contact cause before deciding shield absorption or life loss. It does not clear that cause when the character returns. Completion includes it in the summary.                                                                                                |
| [Ability redeployment](../game/core/abilities.mjs)                       | Impact abandons the live line and enters `respawning` without being a failed attempt. It does not establish a new failure cause; an earlier one may remain.                                                                                                                                                                 |
| [Enemy contacts](../game/core/contacts.mjs)                              | `enemy-trail`, `enemy-player` and `boss-lane` are distinct resolved contact kinds. The lane kind may refer to character or trail contact. Enemy identity is in an event, not in retained failure metadata.                                                                                                                  |
| [Challenge contacts](../game/core/systems.mjs) and core timeout branches | `cut-timeout`, `cable-limit` and `mission-timeout` are authoritative kinds. Length failure occurs when distinct trail cells **exceed** the configured maximum. Mission timeout can end a running or recovering attempt directly, without `player.failed`. Core resolves contact/closure ties; UI must not reinterpret them. |
| Core self-contact                                                        | The seventh kind is `self-contact`. It is resolved on the collision timeline, rather than inferred from how a rendered line appears.                                                                                                                                                                                        |
| [Replay](../game/replay.mjs), `authoritativeCheckpoint`/`verifyReplay`   | Existing versions hash `clock.failureCause` and the terminal result, and compare the full computed summary. A valid replay may end lost. No extra diagnostic event or checksum section is needed.                                                                                                                           |
| [Sessions](../game/sessions.mjs), `suspendSession`/`restoreSession`      | Sessions are only unfinished running/recovering attempts. Replay reconstruction retains prior recovery metadata, but terminal replay adoption is rejected. Loading a session is not an alternative way to import a terminal screen.                                                                                         |
| [App](../game/app.mjs), `eventFeedback`/`overlay('lost')`                | Temporary feedback recognizes some causes. The persistent lost overlay currently names only time/length causes and gives other losses a generic sentence. It already displays revealed percentage and Retry.                                                                                                                |
| App `update`/retry handler                                               | Terminal handling runs once through `handled`, pauses and clears input, and calls the lost overlay without granting an ordinary clear. Retry already recreates the selected mission and resumes.                                                                                                                            |

The critical guard is **terminal status**, not the presence of a cause. A running, recovering or eventually won run may retain a previous contact. Conversely, a mission timeout during recovery must replace that previous cause. Never derive the final reason from `lives === 0`, the last caption, a recent effect, an enemy's later position, or whatever event happened to be last in a render frame.

## Finite text contract

Use original, theme-neutral copy. Keep the existing title “A new line awaits.” and revealed percentage. Suggested final copy is fixed data, not AI-generated coaching or arbitrary pack text:

| Cause                                 | Reason                                                          | Next step                                                                   |
| ------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `self-contact`                        | Your unfinished line crossed itself.                            | Rejoin safe ground without crossing the line you are drawing.               |
| `enemy-trail`                         | An enemy caught your unfinished line.                           | Try a shorter cut while keeping enemies away from the open line.            |
| `enemy-player`                        | An enemy reached your character.                                | Keep a gap from enemies, including patrols on safe ground.                  |
| `boss-lane`                           | An active marked lane caught your character or unfinished line. | Keep both outside the marked lane while it is active.                       |
| `cut-timeout`                         | The time allowed for one open line ran out.                     | Rejoin safe ground sooner. Stopping movement does not pause the line timer. |
| `cable-limit`                         | Your open line exceeded its length limit.                       | Plan a shorter line back to safe ground.                                    |
| `mission-timeout`                     | The mission clock ran out.                                      | Plan a shorter route to the required reveal area and objectives.            |
| Unknown or absent cause on a lost run | That attempt ended.                                             | Review the mission brief and choose another route.                          |

The cut-timer hint refers to stopping movement during play; the real Pause action continues to freeze the simulation. Enemy-player advice does not assert that this particular attacker was a border patrol. “Safe ground” is not promised to protect against every actor. Do not invent a radio failure for fiber craft, a specific enemy name, remaining ammo, a missed boss stage, or a guaranteed winning route from these codes.

Use a short consequence note on ordinary losses: **“Retry starts this mission again. This reveal resets; collected pictures and best results remain.”** For Practice: **“Retry starts this practice again. This reveal resets; practice grants no campaign rewards.”** These explain the new attempt, not a data write. Keep separate storage warnings visible and never say the failed attempt earned or permanently saved a picture. Existing earlier saved-flight data is neither deleted nor promised to resume by this text.

## Pure helper and host wiring

Add `game/ui/retry-view.mjs` with one public projection:

```js
export function retryExplanation(run, options = {}) {
  // Pure display projection; implementation follows this contract.
}
// null outside terminal status "lost"
// otherwise an owned { cause, reason, tip, footnote }
// cause is one of the seven known strings, or null for the fallback
```

Accept the actual run or its summary; only status and cause are needed. Read a bounded set of scalar own data fields, without copying the large grid or retaining the source object. Absent/malformed status returns `null`; a lost run with an unrecognized/malformed cause gets the generic fallback. Do not execute accessors or coerce objects into text. Accept a plain options object (including a null prototype), default an omitted own `practice` field to false, and require any explicitly supplied field to be an own data boolean. Invalid options throw `TypeError`; validate through descriptors before reading rather than destructuring an options getter. Return constants as fresh owned output, with reason at most 120 characters and tip at most 160; no external HTML, actor identifiers or unknown cause strings appear in the result. This helper is a display projection, not proof that a supplied object represents a genuine loss.

The app's existing `overlay('lost')` uses this result through `textContent`, for example reason, tip and the existing formatted reveal percentage in `#overlay-copy`. The consequence note goes in the loss-only `#retry-consequence` paragraph inside `#overlay-reading`; the old lost `#overlay-footnote` is empty. Reset the paragraph to hidden/empty before rendering any overlay so earlier loss advice cannot appear on Ready, Pause or a win. Avoid duplicating the old inline time/length ternary alongside the new helper. No new modal, import option or terminal-state mutation is required. Keep the helper's non-lost guard even though the current host reaches this branch only for lost runs.

`#overlay-copy` and the consequence note share the named `#overlay-reading` region. Retry and Read details/Done stay outside that inner scroll region and must remain reachable without scrolling through every explanation. Keep native keyboard reading behavior. A reader entry/exit still uses the existing preserved-navigation clear path; its mapped Confirm, Back or Menu ends reading rather than activating Retry. Do not focus the explanation on every HUD update or use repeated live announcements.

The Retry handler stays structurally unchanged: it clears demonstration mode, calls `prepare()`, then `resume()`. This uses the current selected level, seed, steering policy and **starting** class/roster. It does not promise to resume the last mid-run switched class. The existing initialization restores the map, objective and encounter state, creates a new run ID/recorder, clears input including controller Toggle Boost and retains collected progress. Test these behaviors instead of replacing them with a new retry subsystem.

Temporary nonterminal life-loss captions remain unchanged. On the terminal lost branch only, replace the transient run message once with “Flight ended. Read the details or try again.” Keep the independent storage warning intact. No first-increment change is proposed for the in-flight Restart button, couch controls/results or Replay Theater. Theater remains a verified recording viewer; a lost recording must not gain a button that silently imports it as a live game. Future reuse of the plain-text helper can be reviewed separately.

### Refinements from actual source-browser checks

On 12 September, the parent's actual 320×640 Playground self-contact loss showed the correct reason/tip and reachable Retry, but the consequence was hidden by the existing compact `.overlay-footnote` rule. The same rule also applies to short landscape layouts. This justified the small HTML/CSS addition above: a hidden-initial, loss-only consequence paragraph inside the scrollable reader, styled at 11px/1.5 with the existing readable text color. It does not rely on the footer that compact layouts intentionally omit. These were source-browser findings, not frozen v0.14 release evidence; final layout acceptance remains in the browser verification record.

Both one-life staged lane-loss checks also left a nonterminal “territory you revealed is kept” caption beside the new reset explanation. The terminal simulation clock does not advance to expire that caption. The narrow correction replaces it at terminal handling with the neutral ended-flight message, while keeping recoverable feedback and the separate save warning unchanged. It adds no event, failure cause or timer change. Recheck contact and lane losses after this correction, including their readable consequence and later Ready/Pause/win transitions.

## Meaningful proof sequence

1. **Projection tests.** Check non-lost suppression despite a retained cause, fresh owned returns and no source mutation. Test null/unknown input, malformed cause, safe own-field handling and non-execution of source/options getters. Confirm that strings resembling markup never enter output. Test the meaningful distinction between consequence notes and their lack of a new-save promise. Actual legal terminal streams below cover each known cause with useful bounded reason/tip output; avoid duplicating every prose string or restating the mapping as a second test oracle.
2. **Legal terminal streams.** In a new focused test file, author small validated levels and use only `createRun`, normal commands, `stepRun(..., FIXED_DT)`, `createRecorder`, `recordInput`, `exportReplay` and verification. For each cause in each turning policy, reach an actual loss and require agreement between live state, summary, replay reconstruction and displayed cause. Use an authored one-life rule where useful; never set status, lives, time, enemy position or failureCause after creation to manufacture the loss. Keep finite tick budgets and report failure to obtain a trace rather than replacing it with a fabricated result.
3. **Specific route controls.** Existing [systems tests](../game/test/core-systems.test.mjs) provide recipes for moving-enemy trail contact, cut time/length limits and timeout, and [Sentinel routes](../game/test/sentinel-playthrough.test.mjs) cover a real lane contact. Add an actual safe-border patrol/body-contact route for `enemy-player`, a returning live-line route for self-contact, and a terminal boss-lane route. Verify the emitted kind because geometric contact priorities can choose a different kind from a visually plausible guess. Include at least one staged level.v2/core.v3 route as well as ordinary level.v1/core.v2 fixtures; do not change their version pairs or existing fixtures.
4. **Retained metadata and restoration.** Produce a nonterminal contact, let the run return, and show that recovery/running states have no terminal explanation. Exercise shield absorption and impact redeployment. Finish a legal win after an earlier contact and require no retry advice despite its retained cause. Separately expire the mission clock during recovery and require `mission-timeout`, not the earlier contact. Suspend a legal recovering prefix, restore it through `restoreSession`, verify the original cause is retained but suppressed, then continue normal input to the final outcome. Check that a valid terminal replay is still rejected by the unfinished-session boundary. No new session field is introduced.
5. **Unchanged authority.** Require exact checkpoint/summary equality for identical pre-existing command streams, and verify that tampering with a replay's expected terminal cause still fails verification. Compare before/after gallery, score, mastery and campaign progress for a real loss plus explicit Retry: no loss award, no duplicate prior award, no deletion of previous collected results. Preserve frozen proof files and their original hashes; new text requires new UI expectations only.
6. **Actual UI acceptance.** Use visible game/Controller Lab controls or clearly labeled replay-backed unfinished prefixes to reach ordinary contact and boss-lane losses in both steering modes. Read the correct reason, use Read details/Done and mapped Back, then explicitly activate Retry once. Before Retry, tick/status must remain terminal; after Retry, one new attempt is running with fresh initial state and neutral-gated controller input. Hold the Confirm used for Retry and verify it cannot repeatedly recreate the run or leak an ability/Boost action. Keyboard/touch activations use the same existing handler. Do not call a replay-backed fixture manual play.
7. **Responsive and regression checks.** At actual iframe dimensions 320×640, 390×844, 844×390, 844×501 and 1280×720, inspect the longest copy, visible/reachable reader exit and Retry, vertical reading, no horizontal overflow and 44px action targets. Successful result/picture view remains unchanged. Exercise reduced effects and muted sound to confirm that the explanation remains textual. Run affected view/reader/navigation/replay/session tests, then the established full gates only after source freeze; finish with candidate/archive verification under the usual process.

These tests establish accurate software behavior, not human comprehension or enjoyment. The user's standing instruction is to continue without requesting another playtest decision. Do not make a human session an approval gate or invent results from one; record comprehension and physical-device usability as unmeasured unless actual evidence becomes available.

## Ownership and version limits

Suggested bounded split: one owner for the pure helper and projection tests; another for new legal failure/replay/restoration tests; the parent for the small app binding and real browser/layout checks. Reuse existing DOM harnesses where they test the real reader/navigation handlers; avoid copying the entire app into a test double or asserting only source text. If a small DOM binding helper is needed for direct callback tests, it must remain presentation-only.

Production files are the new view helper, `game/app.mjs`, and the small observed consequence-placement changes in `game/index.html`/`game/style.css`. Preserve the current region and controls. The [player and maintainer guide](retry-feedback.md) records implemented source behavior separately from release evidence. No changes to core simulation, rulesets, replay/session formats, libraries, packs, mastery definitions, assets, binding preferences or frozen releases are justified by this text-only increment. Any discovered simulation or persistence defect is reported separately before changing that scope.

## Primary-source basis and limits

The [candidate backlog](round-24-candidate-backlog.md) records the primary research reopened on 12 September 2026. [Microsoft XAG 109 — Objective clarity](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/109) supports clear, reviewable next steps; using it to improve the lost-result explanation is a design inference. [XAG 115 — Error messages and destructive actions](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/115) supports explaining a problem and a correction in its input-error context. A gameplay loss is not a form error, and that guidance does not require a confirmation before this immediate Retry action. Page text was inspected; embedded media was not. This plan makes no accessibility-conformance, retention or physical-controller claim.
