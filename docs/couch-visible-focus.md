# Couch shell visible focus candidate

This isolated P03 correction starts at combined P05-B/P08 static source `063ff5d650b6e071d2b59e89fa6e9fb5058b3f08`. It changes only the Couch shell’s local focus helper and its complete host tests. Team, arena layout, shared navigation, operation-focus, picture leases, Start intent, gameplay and saved identities remain on that exact parent.

The native predecessor restored View both boards as the logical focus after leaving the finished-board view, but at 844×390 its 49.30 px control began at y666.55 with scrollY0. The control was outside the viewport. A fresh Shift+Tab scrolled a different action into view; that workaround was not acceptance of the original restoration. All five predecessor samples and their review remain retained separately from the corrected source.

The first held correction fixed board-return focus but still focused Next before the shell wrote result rows above it. Native held01 recorded that remaining first-Results failure. The final correction installs the existing screen, title, result copy and visibility before its one synchronous transition focus; it adds no delayed refocus.

The shell calls `focus({ preventScroll: true })`. It then requests `scrollIntoView({ block: 'nearest', inline: 'nearest', behavior: 'auto' })` only while the same screen, status, navigation root and connected enabled visible action remain current, the document remains foreground, and the actual active element is still that action. A synchronous focus callback may remove the action, select another screen or action, suspend the document, or dispose the shell; those changes prevent the old scroll request. An already-focused current action can still need scrolling after layout changes. This is a synchronous local restoration policy, not a new background-resume or controller-engagement mechanism.

The complete shell/navigation tests assert real host screen transitions, actual focus ownership, exact nearest/auto requests, unchanged run checkpoints and no activation. They do not model rendered viewport geometry. Root’s final native record observes visible first-Results and board-return actions in DOM geometry and accessibility state, including actual 844×390 and 390×844 viewports, with retained results. Full responsive visual acceptance remains **incomplete**: viewport captures contain black bands and repeated edge strips. The capture cause is unresolved; normal captures after override reset are coherent. An already-focused lobby Start also remains outside the viewport after resize alone, a separate P05 follow-up. Physical devices, actual browser zoom, broader layouts and other focus owners require separate qualification.

[W3C’s focus-not-obscured guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) explains why a sighted keyboard user needs to see the focused component. [MDN’s scrollIntoView reference](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollIntoView) documents nearest alignment and scrolling options. These inform this local design; the scoped tests and browser journey do not establish blanket WCAG conformance. The application’s native check also inspects the focus indicator, beyond merely recording `activeElement`. No smooth behavior is requested.
