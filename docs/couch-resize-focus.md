# Couch current focus after resize

This isolated P05 candidate starts at `2c61981b26990b8eb9641ac649300d4a32720746`, which already reveals transition-owned Results and board-return actions. A resize alone has no such transition. The retained native predecessor kept Lobby Start focused at y592.27 in an actual 844×390 viewport with scrollY0, leaving it off-screen. Its Plain/Large/Ukrainian/Rich preferences and DPR1 are part of that observation, not defaults inferred for every player.

The Couch shell now listens synchronously to its own Window's resize event. It reads the current active element, shell screen/root/status and foreground state, then a finite positive layout viewport and element rectangle. It requests nearest alignment only if an edge of that eligible current action lies outside the viewport. After DOM reads it verifies the same current owner and active element again. It never calls focus, chooses a primary action, stores a future opener, engages a controller or changes the round. The existing transition focus/order remains unchanged. Terminal shell disposal removes the listener. An ignored background resize does not replay on return.

The request uses `scrollIntoView({ block: 'nearest', inline: 'nearest', behavior: 'instant' })`. Explicit instant avoids inheriting smooth scrolling from CSS; existing focus scroll margins remain authoritative. This small Window handler does not add an observer, delayed focus job, visual-viewport policy or arena-layout change.

The actual-host tests use one modeled Window and controlled rectangles to verify scroll requests, skipped requests and unchanged live/paused/finished checkpoints. They are not rendered geometry or device proof. A review found a modeled reentrant final style read that could retire foreground ownership without moving activeElement; its before-fix failure is retained. A final currentness check closes that case. Predecessor and successor whole-file results remain separate and non-additive.

[Microsoft XAG 113](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/113) describes the need to keep focus visible. [W3C focus-not-obscured guidance](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) explains focused-component visibility; [MDN resize](https://developer.mozilla.org/en-US/docs/Web/API/Window/resize_event) and [scrollIntoView](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollIntoView) define the chosen event and scrolling behavior. These are design guidance, not blanket accessibility certification.
