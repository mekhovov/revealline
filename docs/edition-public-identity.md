# Edition names and public addresses

Current edition display names use `<edition name> / LINE`. The aggregate Netherlands workshop edition is **DroneAid / LINE**. Its public selector is `?edition=droneaid`, and its standalone launcher is `/editions/droneaid/app/` (beneath the configured deployment base path).

The stable internal identity remains `droneaid-nl-community`. `editionIdentityId()` resolves the public selector, while `editionPublicSlug()` generates public addresses. These helpers live in `game/edition-context.mjs`; the catalog contains one edition, not a duplicate alias record. The separate `droneaid-community` edition remains Community Relay / LINE.

The legacy query and `/editions/droneaid-nl-community/app/` remain supported. Public links generated by providers and tools use the canonical selector. Compilation accepts either selector and records only the stable identity in catalogs, build information, installation records, and offline verification receipts.

## Existing saves and installed apps

Profile keys, session keys, campaign and mission identities, and content ownership remain unchanged. A display-only rename does not change execution entries or presentation receipts. The serialized DroneAid theme name remains its original value because those theme bytes participate in saved presentation receipts; the current catalog supplies display branding separately. Historical presentation snapshots are not rewritten.

The manifest retains its original explicit `id`, `/editions/droneaid-nl-community/`, while new manifests use the canonical `start_url` and `scope`. Installation validation accepts exact old and canonical roots belonging to the same edition, origin, deployment base path, and release version. It does not authorize another edition or arbitrary scope. A canonical launcher reads the existing stable installed-state key and can reopen the saved previous installation before an update is prepared.

## Publication and rollback

The release coordinator and existing admission/review gates remain authoritative. This change does not publish a release. The publisher verifies each frozen manifest, writes its release files beneath the scope that manifest declares, and preserves every original artifact byte.

For a new canonical release, the old launcher path redirects to the canonical launcher and preserves query/fragment state. On rollback to an older frozen release, the canonical launcher path redirects to that release's legacy launcher; the public edition index continues linking to the canonical address. This avoids rewriting historical manifests or losing either launcher entry point.

An already-installed browser can continue serving its old launcher from its existing service-worker cache. The static alias does not force activation, clear caches, or rewrite stored games. Actual installed-PWA manifest/scope refresh behavior still requires browser qualification during release review; the canonical launcher can read the retained installation record independently.

Focused tests cover alias resolution, audience isolation, unchanged progress and presentation identity, installed-state migration and rollback, generated launcher behavior, and immutable publication paths.
