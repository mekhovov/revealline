# Installed startup recovery

New packaged builds check the requested game document's static startup files before opening its cached HTML. The check reads cache keys only; it does not hash the game library, contact the network, check optional chapters, or change the installed-edition selection. The build derives each document's scripts, styles and static module imports from shipped source, including the classic boot's explicit main-module entry.

If a startup file is missing, the edition's existing service worker renders a small recovery page at the requested address. The page and its repair script are produced by the worker itself, so they remain usable when application modules are unavailable. The original query is retained by **Try opening the game**. **Manage installed game** opens the current distribution's bundled launcher with `?manage`, preventing its automatic return to the damaged game. That link is offered only when the shipped inventory includes the launcher; recovery never guesses a parent address. For an immutable edition, its bundled launcher manages that pinned distribution rather than promising discovery through a separate stable launcher.

**Repair game files** is an explicit action. It uses the existing exact-build preparation protocol and verified file checkpoints. Surviving matching files are reused; missing files must match that edition's byte counts and hashes. It neither selects a newer edition nor writes profile, imported-media or soundtrack stores. If the server no longer has the expected rolling-build bytes, repair fails rather than mixing builds; the player can manage updates through the launcher. A successful repair offers an explicit retry and does not reload a running page automatically.

The recovery page has English and Ukrainian copy, keyboard-visible focus, touch-sized controls and safe-area padding. An explicit supported `lang` query takes precedence over the saved language and browser preference, without loading application modules or writing preferences. An observation timeout permits retry, and leaving the page closes its observer without discarding completed verified files. Page return and controller changes keep repair available when a worker is present. Storage denial can still fall back to ordinary online loading.

## Verification and limits

Focused automated checks cover missing entry HTML and required modules, offline recovery resources, no automatic network work or redirect loop, exact verified repair, preserved imported files, rolling/immutable/branded/standalone scopes, escaped return URLs, optional-content exclusion and execution of the repair button's failure/success, timeout, page-return and controller-change states. Build tests check the generated startup closure and existing packaged-worker contracts. The startup guard detects presence, not general corruption; explicit repair retains the existing full byte/hash verification.

These are source and modeled-worker checks. Physical iPhone/iPad Home Screen cold launches, background termination, actual storage pressure and installed update handoff still require the shared device qualification described in [verification.md](verification.md). A resized desktop or passing unit test is not physical-device evidence.

The recovery surface requires the edition's service worker to remain available. Whole-origin removal can erase the worker, launcher and local saves together; portable backups outside browser storage remain necessary. Immutable editions retain distinct addresses. A rolling same-address update is not full core rollback. Existing frozen editions are unchanged.
