# Round 23 — optional controller Boost toggle

Accepted for bounded implementation on 12 September 2026 after independent review found no material contradiction. Baseline: frozen v0.12.0, commit `640f3e3570323394a22922261e8928634db7bf3b`. The requirements below are an implementation contract, not a claim of completed verification. They refine the accepted direction in [the candidate backlog](round-23-candidate-backlog.md) into one bounded **solo Controller Boost: Hold / Toggle** increment. The same option applies to the solo game opened through Playground and Controller practice.

The option removes the need to sustain the controller Boost button. It does not latch direction, accelerate automatically on every new flight, change equipment rules, or claim a complete no-hold control scheme. Couch currently uses its separate `couch/couch-input.mjs` adapter and does not read the solo controller preferences; its Hold behavior remains explicit. Extending this preference to two independent couch players needs a separate ownership and settings decision.

Two existing details make a router-only patch insufficient. Keyboard Stop and the visible Stop button call input-local `clear()`, and pointer cancellation, unexpected capture loss and inactive polls do so too. Also, `eventFeedback` currently displays `player.failed`/`shield.absorbed` without clearing router input. Neither path should acquire a persistent Boost latch accidentally.

## Player contract

**Hold remains the default.** Holding the configured flight Boost button produces the same boolean as v0.12.0. Releasing it stops that controller contribution. There is no activation delay, stamina change, speed change or new core action.

In **Toggle**, a fresh configured flight Boost press changes off→on or on→off once. Repeated snapshots of a held button do not toggle repeatedly. Ordinary physical release leaves an active toggle on. A second fresh press switches only the controller contribution off; a keyboard hold or existing touch latch can still produce Boost.

Pause, Stop, menu/hangar/reader entry, successful binding or mode adoption, attempt replacement, save/load interruption, disconnect, hidden/blur/native interruption and teardown clear the toggle. Returning to flight does not restore it. After clearing, the router must observe eligible physical neutral before accepting another fresh Boost press. Simultaneous pause/hangar/Stop and Boost keeps the existing priority and never activates the latch. The fixed first join gesture remains consumed even if its physical button is mapped to Boost.

Recovery also clears Toggle Boost: losing a life, shield-absorbed contact and impact redeployment all enter `respawning`. Presses during recovery must not queue a Boost toggle. Direction, ability and pickup retain their existing behavior; Hold-mode recovery remains unchanged. When running resumes, a neutral sample and a new Boost press are needed to turn Toggle Boost on again. Merely reaching safe ground or successfully closing a line does not switch it off.

The visible cue describes the requested input, not guaranteed motion: **Controller Boost on · [mapped label] to turn off**. The player may be stationary, constrained by grace or otherwise unable to move. Preserve the existing Boost button's aggregate `aria-pressed` indication for all sources; do not label that aggregate as controller-only.

## Proposed adapter API and state

Use a small dependency-free `game/controller-boost.mjs` helper for the immutable modes and strict `resolveControllerBoostMode(value)` enum validator. It accepts only the two exact strings, without coercion. Omission defaults belong to the constructor/library migration, not to an arbitrary malformed-value fallback.

Extend `createControllerRouter` narrowly:

```js
createControllerRouter({ /* existing options */, boostMode: 'hold' });
router.setBoostMode('toggle');
router.cancelToggleBoost();
router.boostState(); // owned { mode: 'hold' | 'toggle', latched: boolean }
router.sample({ scope, timeMs, toggleBoostEligible: true });
```

The constructor defaults to Hold. A supplied eligibility flag must be boolean; omission preserves existing callers. `setBoostMode` validates before mutation, then adopts and invokes the existing full neutral gate. Invalid adoption leaves configuration, latch, button history and output behavior intact. `setBindings` still validates and compiles atomically and clears the latch on success. No version or extra field is added to the binding document, flight command, UI command or normal router result.

`cancelToggleBoost` is idempotent, does not sample hardware and is a no-op in Hold. In Toggle it clears the latch and disarms only Boost. It must not clear assignment, directional hysteresis, action edges, menu repeats or the host accumulator. Teardown calls are safe; querying state returns an owned snapshot with no mutable internals.

The Boost gate uses the router's existing physical-neutral calculation: mapped inputs in both contexts, enabled stick axes at their release thresholds, and fixed join buttons. This is distinct from emitted canonical `boost`, which may be latched. It can arm only in eligible flight. Preserve the existing rule that one observed neutral sample suffices, including a neutral sample that also lifts the router's full blocked state; do not introduce an undocumented extra neutral-frame requirement. While disarmed, other permitted controller actions keep their existing behavior. An inactive eligibility flag clears/disarms Toggle Boost without changing Hold or the selected scope.

Extend `attachInput` with optional `onClear`, defaulting to a no-op, and a read-only `localBoostActive()` boolean accessor. Call `onClear` after local state has been cleared. The app callback cancels Toggle Boost and removes its cached frame contribution only; it must **never** call `input.clear()` or `clearInput()` recursively. This covers native Stop as well as capture loss/cancellation, and avoids the canonical-neutral deadlock. Existing `poll()` return shape, keyboard/touch semantics and legacy direct-gamepad fallback remain unchanged.

`localBoostActive()` exposes only the adapter's currently accepted local contribution. It does not poll, drain actions, mutate keys, or read hardware. Use it for the precise recovery case below, rather than expanding recorded commands with device provenance.

## Fixed-step recovery and lifecycle wiring

At the normal frame sample, pass `toggleBoostEligible: run.status === 'running'`; the router already prevents flight output outside `scope === 'flight'`. Sample and poll once as today. Keep the per-frame `controls` value owned and replaceable solely for dropping a cancelled controller contribution.

After each `stepRun(..., FIXED_DT)`, inspect the actual transition from running to respawning. This covers `recover()`'s `player.failed` and `shield.absorbed`, and the impact primitive's `craft.redeployed`, without adding or depending on new simulation events. For Toggle only:

1. Cancel/disarm the router latch immediately and update its visible cue.
2. Set the frame's remaining Boost value to `input.localBoostActive()` and remove any cached controller Boost flag. Preserve direction, action, pickup, pending switch and time accounting.
3. Continue the remaining substeps normally. Even if a legal short recovery ends inside this frame, the old controller flag cannot return without a later eligible neutral sample and fresh press.

Record the exact command actually submitted to each tick. The command that caused recovery can correctly contain `boost:true`; subsequent commands reflect the cancellation. Do not retroactively rewrite a recorder segment, call `recordRelease` for this controller-only change, drop `accumulator`, or suppress another genuinely active source. Terminal states already stop further steps and use the existing global clear.

Existing pause/resume/prepare, Settings/hangar, reader transitions, selected-pad disconnect, long-frame pause, native inactive handling, pagehide and BFCache paths must be exercised, not reimplemented. `clearInput` already resets both adapters; adding latch reset there through `router.clear` is sufficient. BFCache remains paused/session-only with invalidated controller ownership. Restoring an unfinished `respawning` attempt starts with Toggle Boost off and ineligible, just like restoring a running attempt starts off and neutral-gated. A mode change or profile adoption must never resume a flight or accept the settings Confirm press as Boost.

## Preference and transport compatibility

Add only:

```json
{ "preferences": { "controllerBoostMode": "hold" } }
```

This is a fragment illustrating the new member, not an importable partial library. Canonical libraries still require their complete existing shape. `DEFAULT_PREFERENCES.controllerBoostMode` is `hold`. After bounded owned-data copying, migrate **only an absent own property** to Hold for accepted library v1 and v2. Explicit `null`, `undefined`, booleans, numbers, other strings, objects, accessors or prototype tricks reject the complete candidate. Never add an active-latch member or infer the mode from a replay's last Boost flag.

Recommend retaining `xonix-library.v2`, `xonix-library-storage.v1` and `xonix-backup.v1`, following the current preference migration pattern. This adds presentation/input preference data, not a new collection record or authority. The separate strict `xonix-controllerbindings.v1` remains unchanged. **Compatibility is forward, not bidirectional:** frozen readers with exact preference-key checks can reject a new export containing this member, even when it is Hold. A v3 library label would not make those readers compatible; do not silently strip the setting or promise a downgrade export. Document the added member and omitted-only migration explicitly.

The oldest whole-library release supported by current earlier-collection discovery is v0.2.0 (`release` channel, library v1); v0.2.1 onward uses versioned release channels. Import those real original profiles and the latest v0.12 library v2 with Hold as the normalized default. Preserve source bytes and generations during discovery/preparation. Pre-library per-campaign progress from earlier releases is outside current automatic discovery; this increment must not claim or invent a new migration for it. [The older controller-preference note](controller-preference-migration.md) records the original v1-era addition; the actual current format is v2.

Existing per-key `mergeLibraries` behavior should keep a newer Toggle preference when a stale tab saves unrelated audio/progress changes from an omitted→Hold baseline. A deliberate Hold change is allowed to replace Toggle. Adopt the library returned by `saveLibrary`, not the unmerged candidate; constructor, mode control, `adoptPreferences`, controller hints and router mode must agree. Invalid imports fail before decoding pack images and before adoption. Full-backup, player-library and earlier-release import/Undo restore the mode as metadata, while clearing the active latch every time. Transfer fingerprints include the newly normalized preference; compare prepared old/current snapshots with the same current validator, without rewriting archived hashes.

Session-only editing remains useful in Practice, secondary tabs, blocked storage, unavailable locks and BFCache returns. Keep the requested valid mode in memory, show that it is session-only, and let player-library/full-backup export retain it. Do not claim that **Export flight** retains preferences: `xonix-session.v1` contains `campaignKey`, `themeId`, `bodyId`, `runId`, `savedAt` and its replay, and restores under the current profile's input preferences. No writer lease, generation, backup journal, lock or Undo relaxation is needed.

## Settings and Controller practice

Add a normal labeled select, **Solo controller Boost**, with **Hold** and **Toggle** choices and concise help: “Toggle: press Boost once for on/off. Stop, pause and recovery turn it off. Direction still needs a hold.” Place it outside the binding draft so it does not become an undeclared binding field. Its native `change` adopts the scalar; existing controller select navigation previews until Confirm and Back cancels without a write. Make it clear that the binding editor's defaults reset its button/stick draft, not this separate setting. Selecting Hold is its reset.

Pause before editing, use existing preference persistence, then adopt the resulting mode and clear input. Refresh on Settings open, import, Undo and profile replacement. Display saved/session-only feedback using the current result, not a stale `saveSucceeded` value from some unrelated setting. Closing Settings keeps the prior paused/ready/result state; Resume remains a separate action.

Provide a stable controller-specific cue near existing flight controls, using actual configured labels and text rather than color alone. Announce changes only when mode, latch or mapped label changes, not every frame. Keep the global Boost control's mixed-source state accurate. Verify no overlap with the picture, encounter notice, appearance reward or reader toolbar at actual 320×640, 390×844, 844×390, 844×501 and 1280×720 viewports; interactive targets remain at least 44 CSS pixels.

Use the existing Controller Lab's physical-index buttons, Pulse/Hold gesture selector and sixteen-button/four-axis transport. No envelope change, extra state injection or private iframe hook is needed. Explain that **Release all** releases physical buttons/sticks; a normal release alone does not switch a live game toggle off. Use configured Boost again or Stop for that. Parent focus loss may separately pause/clear the game, so record actual focus/lifecycle rather than attributing such a clear to release semantics. Stick editing intentionally relinquishes game focus and is not a continuous in-flight hold experiment.

## Research and evidence limits

Microsoft's [XAG 107 — Input](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/107), reopened for this plan on 12 September 2026, distinguishes remapping from prolonged-hold demands and recommends considering toggles while preserving the action's functionality. This is the same primary source attributed in the candidate backlog. Only its page text was inspected; embedded images and videos were not reviewed. The proposed input option follows that guidance, but software tests and a virtual controller do not establish accessibility conformance, physical comfort, retention, real Bluetooth behavior or native-device operation. Those remain separate observations.
