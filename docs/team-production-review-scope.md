# Team production review scope

The production generator fingerprints Team recipes separately from Solo effects. Previously, new Team Support, emitter, rescue and outcome slots belonged to the effects inventory group and could receive the existing reviewed Solo effects declaration, whose inputs contained no Team painter. Source grouping and inventory grouping now have separate purposes.

All 42 Team roles use a dedicated fingerprint covering the Team painter, actor/objective/Support/emitter/rescue/pilot/enemy/outcome helpers, runtime slot selection, shared actor presentation and slot catalogue. The generator retains their source-stage status until an explicit Team review is recorded. Existing Solo recipe review declarations are unchanged. This creates no new review approval and does not replace existing ledger bytes.

The regression test runs the actual production constructor, verifies every Team role and its exact provenance, and independently changes every declared input to prove the Team fingerprint changes. On the original generator it exposes Team Support as incorrectly reviewed.

Release adoption must regenerate the production ledger while preserving immutable history, inspect both arenas and all Team states using those generated assets, and record bounded evidence before declaring them reviewed. Optional historical compatibility does not establish complete curated Team coverage. Source tests alone do not prove visual quality, fairness, physical input or public deployment.

The release builder calls `retainFieldKitProductionHistory` for the explicit 42-role migration. It preserves every existing slot contract and immutable record, appends only the exact registered Team contracts/default assets, and adds production bindings in one document revision. An altered existing slot, unregistered role or incomplete role set is rejected before adoption. Subsequent generation preserves the historical slot order and reproduces the same bundle bytes. The generic history writer still rejects slot changes. Reproduction tests for the current production builder follow that explicit path; historical fixture and generic mutation tests retain the strict writer.

The integration release must regenerate the ledger and compiled assets before running reproduction checks. Tests that require the committed current ledger to equal the generator are expected to fail against the old 293-slot ledger; their equality assertions remain intact. Source-bound UI and Team approvals remain independent gates.

Canonical-main reconciliation starts from the authenticated main fpv57 ledger, not the archived unpublished Journey fpv55–58 lineage or an old Team fpv59 preview. The migration regression reconstructs pre-Team fpv57 from the existing `production-main-reconciliation.json` oracle: exact group prefixes, all 127 payload hashes, and the complete exported bundle hash must match before the generic writer rejection or explicit migration is tested. The first additive migration must produce fpv58. A separate current-ledger regression checks prefix preservation, repeat byte equality and the generic writer's no-op behavior after the contracts are installed. This keeps the rejection test meaningful after generated production is adopted without changing the historical oracle.

Keep current exact Team picture bindings and host fixture revisions until the newly generated canonical successor has been reviewed; update those explicit identities together. The changed presentation host reopens the UI fingerprint and does not inherit its previous review. Generation, static composition and fixture reconstruction grant no artwork or release approval.

The shared presentation host admits only explicit Team image slots. `team-runtime-slots.mjs` is the dependency-free authority for the eight frozen slot groups and pilot states; existing painter modules re-export those same objects. Both UI and Team recipe fingerprints include this leaf. Changing slot authority reopens both reviews; unrelated Team drawing changes reopen Team only. The extraction preserves all 42 slot identities and aggregate order, and grants no UI, Team role or artwork approval.
