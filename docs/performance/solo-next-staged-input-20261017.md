# Ten-Next route semantics correction

The prospective ten-Next correctness workload remains unreleased. Its separately fixed public Auto Next preference does not establish that every planned route can survive input-delivery delays. The historical twelve-arm cohort, ten observed recordings and their original failures remain unchanged. No native qualification or performance pass is inferred from the controls below.

Earlier direct-core route exploration omitted two Main Solo input behaviors: releasing a direction key does not stop continuous steering, and `capture.stopped` makes the host clear input before later substeps. The earlier positive Two Keepers route was therefore exploratory, not a proven public-input recipe. Its attempted staged translation also removed safe post-capture/border dwell, changed enemy phase and failed its nominal final cut. Those results are retained; no duration search was continued.

The corrected cache model uses exact a6 production `attachInput`, the host's capture-clearing boundary and the 120 Hz simulation. It delivers separate modeled keyboard events at declared times, samples input once per callback and records every accepted simulation command. It never assigns positions, enemies, progress or gameplay state. Node events are not trusted browser events; this is a source-level control, not native input evidence.

One fixed Two Bays route observes the foundation row, first capture, reclaimed column, top capture, a declared safe dwell, lower reclaimed row and final capture. It stops on a lost life, unexpected state or deadline. The same route was tested at 30/40/45/60/90/120/144 Hz with 0/16/50/100 ms per-event delivery delays. Route/stage bounds are 60/15 seconds; at most 64 delivery records are retained.

Releasing the old key before pressing the next wins 14/28 cases: all cadences at 0/16 ms. Continued Up intent during the two round trips moves the first horizontal cut away from its intended row, and every 50/100 ms case loses before that capture completes. Pressing the next distinct direction before releasing the old key improves this to 18/28. Every 100 ms case still loses on the first cut; at 50 ms, 45 Hz loses there and 90/144 Hz lose near the final safe landing. All 56 generated recordings reconstruct exactly in the same Node engine. All failed variants remain retained.

Four direct input-owner controls verify the proposed ordering and its limits: fresh next-direction keydown changes intent, later old-key release preserves it, capture clearing does not make a held physical key fresh, and repeating that direction requires its own keyup before the next keydown. The model retains these rules; it does not manufacture simultaneous native actions.

The next route design must establish safe position and enemy-phase boundaries that remain valid under actual input latency. Wider millisecond schedules, automatic retries, lower goals/life requirements or altered final-mission assertions do not address this evidence. Any eventual candidate-only declaration still needs the public false preference, eleven accepted mission identities, ten actual manual Next transitions, all existing scenario deadlines and strict same-engine final replay. Historical 8b cannot honor that preference and cannot supply a matched manual-Next comparison.
