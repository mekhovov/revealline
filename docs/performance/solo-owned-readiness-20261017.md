# Owned readiness before Solo Start and Resume

The frozen a6 native timing observations remain unchanged and unqualified. Among 23 observed candidate rows in the four timing cohorts, 15 had a completed internal cadence baseline and eight retained only 1–29 of the required 30 preparation samples. Rapid Start could therefore leave the decorative policy at its provisional 60 Hz baseline for the entire run. This is a readiness defect; it does not explain every observed hitch.

The new source waits for 30 quiet foreground callbacks before accepting the first Start or a restored run's first Resume. It uses the existing 4–50 ms interval and less-than-3 ms application-work criteria, upper-median calculation, native callbacks and 120 Hz simulation. A completed pre-play baseline is reused. An incomplete earlier title sample set is counted separately and restarted under the current attempt. Loaded gameplay never recalibrates the baseline.

The quiet stage has one 10-second deadline. Unsupported or persistently busy cadence remains paused with a localized retry message; it is never silently labeled 60 Hz. The existing accepted interval range covers the tested 30/40/45/60/90/120/144 Hz schedules. Cadences outside 20–250 Hz can fail this finite readiness criterion and require an explicit retry; no broader compatibility qualification is claimed. The user-facing text says “Getting ready. Gameplay is paused.” or “The game is not ready yet. Try Start or Resume again.”

The attempt still activates permitted audio in the original user gesture. Blur, hidden state, cancellation, replaced attempts, renderer loss and scene shutdown invalidate the waiting lease. A benign paint revision does not erase valid cadence samples. If painting changes during preparation, the replacement board must be prepared and submitted before the first simulation tick. The existing native observer's read-only `readyCount` alias is preserved.

A separate actual-host control demonstrated another preparation gap: the public Dnipro Porcelain theme was selected with six pending font requests, yet Start reached `running` while the previously accepted Industrial Workshop theme was still active. Resolving the fonts then changed CSS and invalidated the scene during play. The retained control is `.cache/solo-followup/c41-successors/deferred-font-host-result.json`; this was a modeled FontFaceSet boundary, not native font timing or attribution of the recorded 384 ms task.

Start now awaits the existing shared theme owner's finite, abortable `whenReady` lease before choosing accepted appearance and preparing the board. Cached Resume takes this path when a selected theme is still preparing. Attempt cancellation does not cancel shared fonts. A new selection after the awaited stage keeps the game paused for a fresh explicit activation. Theme preparation timeout uses the same plain retry feedback, with the precise failure retained only in manual diagnostics. The theme-owner implementation and owner tests are separately committed as `081146120`.

Manual paused diagnostics also record `secureContext` and URL `protocol`, without the full address, automatic upload or per-frame allocation. They identify a qualification condition; they are not evidence that HTTP or browser security caused the user's problem.
