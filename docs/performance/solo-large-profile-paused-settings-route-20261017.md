# Large-profile WebKit: three separate failure mechanisms

All historical six WebKit arms remain failed. The complete native cohort is published in `docs/performance/solo-final-large-profile-outcomes-20261017.md` (commit `eb3d11134`); this follow-up changes no runtime or dispatched declaration.

1. **Candidate r1/r3: startup interruption before profile import.** The first running window reaches the existing long-frame pause on 313/284 ms intervals. `#pause-button` then becomes hidden, so the original 30-second click fails. Exact a6 `game/app.mjs:13003` samples elapsed time before `update(dt)`; recorded 202/230 ms update spans include interruption handling and cannot explain the already elapsed interval by themselves. The same update calls the normal pause/save/HUD path. No profile bytes were submitted. These rows remain failures, with no automatic resume or reclassification as profile pressure.
2. **Baseline r1/r2/r3: unresponsive paused page, cause unresolved.** The public Pause and paused-state wait pass. Initial `#shell-menu` click times out without an interception/hidden diagnosis; even the following body attribute read times out. The final recovered probe retains paused callback gaps of 76,900/76,998/77,872 ms; measured completed application work around that boundary is only 6–21 ms. The gaps are outside attribution offered by these sparse work spans. Final state is paused/ready/visible, but inner browser cleanup remains unconfirmed; independent outer owners close cleanly. No profile import, CPU stack, input event receipt, visibility history or native dialog event witness identifies a single source cause. In particular, the failed click does not prove its handler ran. A selector change is not a demonstrated repair for these baseline stalls.
3. **Candidate r2: Home still intercepts Resume after Escape.** Exact profile import and reload complete. Library and Settings closes pass, action 24 delivers Escape, but action 25 repeatedly reports the open `#shell-home` intercepting the visible enabled `#start-button`. This proves an open modal at the Resume click; it does not establish whether the preceding Escape generated a native close request, was consumed by a reader/editor/More view, or was prevented. Those events and focus were not retained. No runtime menu rewrite is justified by the available evidence.

The official [Playwright actionability documentation](https://playwright.dev/docs/actionability) requires a clicked target to receive pointer events; forcing or dispatching the Resume click would remove this proof. The [HTML close-watcher rules](https://html.spec.whatwg.org/multipage/interaction.html#close-watcher-infrastructure) also distinguish delivered keyboard input from a completed close request. These describe the semantics, not an attribution of the actual WebKit failure.
