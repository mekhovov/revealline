# Optional resource owner accounting

The prospective accounting change distinguishes an owner that has never been constructed from a missing, failed, retired or disposed owner. It changes manual diagnostic exports and their bounded reader, not resource budgets, preparation, playback, simulation or numerical gates. Historical missing counters remain unknown; no retained report is rewritten or promoted.

Published PCM and the soundtrack player expose a fixed `SoloOptionalOwnerStateV1` record. State enters `creating` before constructor invocation, becomes `active` only after assignment, and never returns to `never-created` after failure, removal or disposal. A mismatched live reference is `unavailable`. A previously closed owner can remain readable after replacement fails; its actual counters stay visible, but its `failed` state remains explicitly uncertain.

Only the witnessed never-created state emits explicit zeros for that owner's retained PCM, inspector worker/request/bytes and player-owned Blob URLs. The existing 32 MiB published PCM limit is reused. The new empty `decks` array means no committed soundtrack-player deck records. `bootstrapMediaElementCreated` separately acknowledges the first HTMLAudioElement created before the local-recording lookup and player constructor. Zero player counters do not establish zero media elements, decoder memory or browser allocation.

The shared preparation queue is always observed. Its actual snapshot is read once from the player receipt, or from the existing shared owner before the player exists, and reused for both resource views. Active fetch/decode work and reservations can therefore coexist with zero player-owned resources. The duplicated admission views must not be summed, and reservations remain declared estimates rather than native-memory measurements.

The reader accepts an empty deck table only with the exact new never-created witness and explicit zero fields. It rejects positive or missing zero claims, malformed metadata, an active player without its bootstrap witness and disagreement between the shared admission views. Other lifecycle states retain unknown status even when an actual closed owner exposes zero counters. These checks apply per snapshot: a later document may legitimately have a fresh owner, so no cross-document lifecycle monotonicity is assumed. Every snapshot, failed raw verdict and existing resource/output limit remains retained.

## Controls and scope

The cache prototype exercises fresh export without audio/context/fetch creation; constructor failure before assignment; actual closed-owner retention after failed replacement; lost references; disposal; and a cancelled shared decode whose reservation persists until settlement. The modeled Solo host holds the actual cache-storage lookup after an HTMLAudioElement exists, observes zero player counters plus a nonzero shared reservation, then permits the real player constructor. A separate failed-bootstrap/disposed-host control preserves unknown fields. The bounded snapshot writer round-trips the new scalars without changing its byte/count limits. The immutable legacy resource fixture retains its unknown counters and raw failure.

Initial prototype evidence is retained under `.cache/solo-followup/resource-owner-lifecycle-proposal/patch/`. The first loader invocation accidentally used the unchanged source and is retained only as an old-source control (26 tests). The first changed-source pure group passed 31/32; its sole failure was a negative fixture that assigned the already-current queue phase. A later chunk control exposed macOS `/tmp` canonicalization and was corrected to use the actual path, without weakening the writer. The first complete group retained 168 passes, one path-fixture failure and one cancellation at the mistakenly narrow 180-second outer file bound. The existing long Retry case and earlier cadence model require their existing finite bounds. These initial results are not replaced by later checks.

The complete six-file affected group subsequently passed 174/174 in 93.98 seconds (`complete-tracked-v2.tap`, 39,089 bytes, SHA-256 `028082622dd79f4d33b59264af67d00621b8a58f29c33c39153b04bef43d76da`). Final review then moved the existing paused-export check before all optional-owner reads. The complete changed Solo host file passed 12/12 in 102.00 seconds, including a control of the actual exported method that rejects active play before touching an owner (`host-final-v3.tap`, 3,144 bytes, SHA-256 `5a47563252d02663b69f3121608761009fbeabaed69db876bf099e76bec230db`). The unchanged five files did not need another run. Scoped lint, formatting and diff checks passed, and an independent source review found no additional lifetime or authority issue.

No native memory or gameplay qualification follows from accounting completeness. Future native observations require the actual new production source and artifact; the older initial unknowns are not repaired retrospectively.

## Interval and callback-work attribution

`performance-session.mjs:recordFrame()` attributes the elapsed interval to `previousPhase` (or hidden when appropriate). It also attributes the current callback's work to that same prior phase before saving the current phase. A callback that detects an interruption and paints the pause response can therefore contribute pause-response work to playing bins. This preserves evidence; it does not prove that the response caused the preceding gap. No bins, failures or gates are removed or lowered here.

Phaser PRE_STEP through POST_RENDER includes synchronous render submission. HUD and simulation costs are nested component observations and must not be added again to total update work. Compare raw journal endpoints and boundary phases when investigating a hitch. A native long task can overlap smaller measured work windows; the retained Long Rail 384 ms task was not explained by a measured work window of at least 50 ms, but was not established to be wholly outside Phaser. The CPU profile spans startup, preparation, play and public UI without a complete profile-to-page clock bridge. Its font/image samples do not by themselves explain recurring active-play p95, browser raster work or physical-device behavior.
