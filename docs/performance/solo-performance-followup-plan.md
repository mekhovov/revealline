## Research review and resulting decisions

- **Keep the published HTTPS environment in the device record.** WebKit maintainers confirm that Safari 27 can apply enhanced-security restrictions to plaintext HTTP navigation. The user's published-HTTPS clarification removes that specific local-development explanation; it does not establish which other browser policies were active. Keep the existing security settings during qualification. [WebKit issue and maintainer confirmation](https://bugs.webkit.org/show_bug.cgi?id=324968).
- **Record the actual Safari release alongside rendering evidence.** Safari 27's release notes include fixes for large-radius blur loading, unnecessary Canvas2D compositing layers and progressively sluggish ResizeObserver callbacks. These examples support testing first draw, restoration and sustained callbacks on the actual browser; they do not establish that any listed bug caused this game's slowdown. Keep bounded decorative effects and paused layout preparation, without adding version-specific workarounds from these reports alone. [Safari 27 release notes](https://webkit.org/blog/18325/webkit-features-for-safari-27-0/).
- **Prepare the final layout before Start.** CSS Font Loading specifies that ready follows relevant font/layout work, while later changes can create another readiness cycle. WebKit's ResizeObserver example also shows layout can run again after observer changes. This supports the implemented paused final-layout owner and boundary checks; it does not attribute an old native interruption. [CSS Font Loading](https://www.w3.org/TR/css-font-loading/), [WebKit ResizeObserver](https://webkit.org/blog/9997/resizeobserver-in-webkit/).
- **Observe completed native input after its command boundary.** The HTML callback cleanup rules permit a microtask checkpoint between native event listeners; a programmatic dispatch can keep an outer JavaScript stack alive and defer that checkpoint. Therefore a capture-listener microtask is not a reliable completion witness. The new Cancel protocol retains early evidence and reads the real state after the existing awaited native key command, without an added delay or application hook. [HTML callback cleanup](https://html.spec.whatwg.org/multipage/webappapis.html#clean-up-after-running-callback), [native/programmatic example](https://jakearchibald.com/2015/tasks-microtasks-queues-and-schedules/index.html).
- **Check the actual selected face.** FontFaceSet.check() can return true without a matching face; it is not definitive loaded-font proof. Keep the raw check value, inspect the bounded exact family/weight/status at preparation boundaries and retain the transport owner. [Specification](https://www.w3.org/TR/css-font-loading/#font-face-set-check).
- **Keep font status separate from promise settlement.** In the exact upstream WebKit revision used by the retained hosted browser, internal `TimedOut` maps to public `error` without rejecting the face's `loaded` promise; the swap display policy can enter that state immediately. This explains why the prior all-faces-loading predicate cannot establish request failure. Observe stable face identities and the application's existing load promise, including its returned faces, without requesting additional fonts. Preserve the old failed result and treat unused duplicate declarations separately from requested faces. This is a diagnostic correction, not an attributed iPhone defect. [Pinned FontFace implementation](https://github.com/WebKit/WebKit/blob/343e13bf22dca9d0ec227801419aab0f9001a32f/Source/WebCore/css/FontFace.cpp#L311), [pinned display timing](https://github.com/WebKit/WebKit/blob/343e13bf22dca9d0ec227801419aab0f9001a32f/Source/WebCore/css/CSSFontFace.cpp#L541).
- **Separate browser delivery from synchronous application work.** Long Animation Frame duration and input blocking measure different things; several shorter tasks can still delay a frame, and the API excludes ordinary 20–40 ms misses. Keep numeric callback evidence alongside application work. [Chrome timing examples](https://developer.chrome.com/docs/web-platform/long-animation-frames).
- **Record the WebKit port and backend.** WebKitGTK's 2.52/2.54 examples describe GPU-dependent tiling, deferred drawing and compositor-thread work. These explain why synchronous submission cannot account for every frame cost. They do not prove those implementations ran in our hosted browser or caused its misses, and Linux WebKit is not iPhone Safari. [2.52 examples](https://webkitgtk.org/2026/03/18/webkitgtk-2.52-highlights.html), [2.54 examples](https://webkitgtk.org/2026/09/16/webkitgtk-2.54-highlights.html).
- **Do not enable low-latency canvas hints without a device experiment.** Chrome's `desynchronized` example bypasses some compositing but documents tearing/flicker and canvas-overlay restrictions; feature support must be checked through actual context attributes. The current prepared board and DOM controls stay intact. Treat this as a separate device experiment only if profiling attributes remaining latency to compositing, not as an assumed Safari/Steam Deck fix. [Chrome example and caveats](https://developer.chrome.com/blog/desynchronized).
- **Use workers for the demonstrated JavaScript computation.** PROXX shows improved responsiveness can coexist with longer total processing. Web Audio already performs decoding off the control thread. Keep the static MP3 structural-inspection worker, bounded transfer/ownership and existing streamed music; do not move the entire renderer or decode soundtrack recordings to PCM. [PROXX case study](https://web.dev/articles/off-main-thread), [Web Audio algorithm](https://www.w3.org/TR/webaudio-1.0/#dom-baseaudiocontext-decodeaudiodata).
- **Defer complete optional features and test their first use.** Google's code-splitting examples reduce startup evaluation by loading a feature on demand, while warning that unbundled module trees can introduce request waterfalls. Apply this to the unopened Library owner and its exclusive graph, with explicit loading/cancellation and unchanged public menu behavior. Verify the production/offline closure and cold menu opening separately. Source bytes removed from the eager graph are not a measured time saving, and splitting every small helper is not a performance goal. [Code-splitting examples and tradeoffs](https://web.dev/learn/performance/code-split-javascript).
- **Separate yielding from admission.** Breaking a task into smaller pieces gives the browser opportunities to respond; it does not prevent those pieces competing with the next gameplay frame. The idle-callback specification also discourages continuously scheduled callbacks that do no useful work. Keep the game's explicit phase gate for optional replay verification, wake it through existing lifecycle changes and retain bounded chunks when permitted. This is an application policy, not a claim that a scheduling API guarantees frame deadlines. [Chrome long-task examples](https://web.dev/articles/optimize-long-tasks), [Cooperative Scheduling specification](https://www.w3.org/TR/requestidlecallback/).
- **Preserve a real task boundary for terminal optional work.** The new first-victory profile justifies removing duplicated identity validation and admitting optional replay serialization separately. Chrome's long-task example uses a future task, with a timer fallback when yielding is unsupported; an already resolved Promise alone does not provide that opportunity. Retain the existing scheduler and cancellation owner rather than relying on an optional API call that becomes only a microtask in Safari. Required durable-save work keeps its existing guarantee. [Cross-browser yielding example](https://web.dev/articles/optimize-long-tasks).
- **Do not confuse a prioritized continuation with idle work.** Chrome's `scheduler.yield()` examples show that continuations can run before other tasks of the same priority, and inherit background priority only when explicitly scheduled that way. An unconditional API substitution would not establish the game's active-play exclusion. The idle-callback draft also warns that promise continuations and layout may add work after the callback returns. Keep the explicit owner and include downstream work in separate profiling; no new polling loop or scheduling polyfill is needed for the demonstrated fix. [Chrome continuation examples](https://developer.chrome.com/blog/use-scheduler-yield), [idle deadline accounting](https://www.w3.org/TR/requestidlecallback/#idle-periods).
- **Reduce hidden work and measure sustained behavior.** WebKit recommends stopping hidden animation and unnecessary background work. Preserve idle suppression, optional-preparation admission and owned offline pauses, then verify warmth/background behavior on actual devices. [WebKit power guidance](https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/).
- **Inspect actual canvas surfaces and keep capture separate.** WebKit's canvas tooling exposes commands, dimensions and memory, while its timeline documentation warns that capture can affect performance. Profile only separate diagnostic runs; theoretical viewport pixel count and sample counts are not raster duration. [Canvas example](https://webkit.org/blog/8452/canvas-debugging/), [timeline limitations](https://webkit.org/web-inspector/timelines-tab/).
- **Separate thread activity when investigating warmth.** WebKit’s CPU timeline distinguishes main-thread work from engine and other thread activity and supports exporting the recording. In a separate diagnostic session, correlate the same loading or Demo interval with those categories; low synchronous application counters cannot account for all browser CPU usage. Enable only the required timeline and keep the recording separate from qualification timing. [WebKit CPU timeline example](https://webkit.org/blog/8993/cpu-timeline-in-web-inspector/).
- **Compare retained memory after repeated operations.** WebKit's memory example separates JavaScript, decoded images, graphics layers and other page memory. Its repeated-operation comparison distinguishes one-time cache growth from continuing retention; a heap snapshot also performs garbage collection. Keep these diagnostic runs separate from timing, compare the same settled transition boundaries, and do not interpret bounded JavaScript buffers as proof of total browser memory stability. [WebKit memory debugging example](https://webkit.org/blog/6425/memory-debugging-with-web-inspector/).
- **Check the reported Safari canvas-text retention separately.** WebKit issue 324693 remains an open report of graphics-process memory growth with changing Canvas2D strings and downloadable fonts on iOS 27. Source inspection finds changing recovery and Classic power-up countdown labels in `game/ui/event-feedback.mjs` and `game/ui/classic-view.mjs`; queued arrows and target-order labels have a small vocabulary, and the main HUD clocks are DOM content. This overlap is a test hypothesis, not attribution. On the actual iPhone, compare settled graphics-process memory and canvas commands during repeated recovery/power-up activity, keeping the same font, scene and cadence. Do not ship shadow/font substitutions or claim a fix without a matching reproduction and visual checks. [Open WebKit report](https://bugs.webkit.org/show_bug.cgi?id=324693).
- **Keep desktop stress in scope.** Chrome's calibrated-throttling example shows GPU differences can make a phone slower than a CPU-throttled desktop prediction. Use desktop stress as evidence, then qualify the user's devices under recorded cadence, power and sustained conditions. [Chrome example](https://developer.chrome.com/blog/devtools-grounded-real-world).

Completion means demonstrated removal of application-caused stalls within the declared qualification scenarios. It cannot guarantee behavior against browser scheduling, driver failures or thermal throttling. Current results do not yet meet that completion condition.
