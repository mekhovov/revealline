## Review decisions

The original phases 0–4 remain the implementation direction. Native callbacks, real elapsed time, prepared assets, bounded media admission, cached board layers and presentation-only adaptation address demonstrated costs. This follow-up closes evidence gaps and fixes concrete defects found by qualification. It does not introduce a renderer rewrite, smaller simulation step cap or universal frame-rate guarantee.

1. **Establish a complete test result.** Two failing PR jobs reproduce seven presentation fixture failures. Their assumptions predate the scene-clock reset and retained paused canvas. Correct fixtures must preserve presentation, persistence and checkpoint assertions. A subsequent reward audit also found a real regression: throttling every interface refresh can let an immediate Retry/Next replace the winning run before mastery observes it. Run identity/status transitions require immediate refresh; ordinary polling remains bounded. The earlier interrupted broad run has 234 failures, including confirmed original-main defects and unclassified cases; a passing subset cannot replace a full inventory.
2. **Calibrate CPU stress on this host.** The earlier 4× setting is useful stress evidence but is uncalibrated. Add a reproducible local calibration using Chrome's benchmark and score targets, record every sample and independently verify the selected rate. This still does not reproduce mobile GPU, memory bandwidth or thermals. [Chrome calibration guidance](https://developer.chrome.com/docs/devtools/settings/throttling), [device-comparison limitations](https://developer.chrome.com/blog/devtools-grounded-real-world).
3. **Exercise real work and retain failed attempts.** Border movement with muted audio does not qualify captures, erosion, jammers, combat, recording, music or transitions. Native scenarios must use legal controls and check public outcomes. Fixed-tick model proofs remain correctness evidence. A route that fails under wall-clock input must be recorded as failed; state injection cannot make it a performance pass.
4. **Separate cache states and instrumentation.** Playwright request interception disables its HTTP cache. The existing access fixture therefore cannot prove a cold-versus-warm HTTP comparison. Label that limitation or move only the explicit local access fixture to the server. Run timing separately from screenshots, CPU/allocation profiles, heap snapshots and forced collection. [Playwright route behavior](https://playwright.dev/docs/api/class-page#page-route), [Chrome memory tools](https://developer.chrome.com/docs/devtools/memory).
5. **Measure resource stability without destroying the workload.** Compare the same paused state after repeated transitions, covering owner counters, JavaScript heap and DOM retention separately. A heap snapshot forces collection and omits some native/GPU allocations. `Memory.prepareForLeakDetection` also terminates workers and drops caches, so it is unsuitable for live-owner plateau checks. [Heap snapshot behavior](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots), [CDP Memory methods](https://chromedevtools.github.io/devtools-protocol/tot/Memory/).
6. **Use explicit yielding only where measurements justify it.** A resolved promise does not yield to rendering. Substantial remaining optional preparation can use feature-detected `scheduler.yield()` with a task fallback, batching work to avoid excessive overhead. Authoritative ticks, integrity checks and durable-save guarantees remain intact. [Task yielding guidance](https://web.dev/articles/optimize-long-tasks).
7. **Keep Safari findings evidence-based.** Inspect actual canvas/composited surfaces and focused styles before changing them. A historical WebKit canvas/outline report is a useful diagnostic example, not proof of a current iPhone 17 Pro defect. Preserve visible keyboard/controller focus. Use separate Web Inspector CPU/canvas captures for physical diagnosis. [WebKit report](https://bugs.webkit.org/show_bug.cgi?id=248460), [Canvas inspection](https://webkit.org/blog/8452/canvas-debugging/), [CPU timeline](https://webkit.org/blog/8993/cpu-timeline-in-web-inspector/).

## Acceptance gates retained

Record foreground callback interval **B** during lightweight preparation and keep it fixed through loaded play. Work p95 must be at most `min(10 ms, 0.6 × B)`, callback p95 at most `1.2 × B`, callback p99 at most `2 × B`, missed opportunities at most 1%, and application input-to-render submission p95 at most `2 × B`. Diagnostics overhead must be at most 5% in matched runs. Investigate every consecutive-miss burst and every active task over 50 ms; preserve all intervals over 33/50/100/250 ms. No reproducible application-caused foreground stall of at least 100 ms or overload pause is acceptable. Resource bounds and stable retention must hold across transitions.

Event Timing is supplementary: it excludes continuous movement and has duration thresholds/rounding. Keep application event-to-simulation-to-render instrumentation for continuous controls; it measures submission, not physical input-to-photon latency. [Event Timing limitations](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceEventTiming).
