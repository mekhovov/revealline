## Web research and implementation decisions

- **Remove avoidable layout reads before changing rendering architecture.** Chrome's forced-reflow guidance describes how geometry queries after DOM/style changes force synchronous layout. The profile's repeated feedback measurement and the unused touch reads justify the narrow fixes already implemented. Native tracing must still establish their actual effect. [Chrome guidance](https://developer.chrome.com/docs/performance/insights/forced-reflow), [Resize Observer specification](https://www.w3.org/TR/resize-observer/).
- **Workers improve responsiveness, not necessarily total cost.** The OffscreenCanvas examples demonstrate moving canvas work away from main-thread input, but require changed canvas ownership and DOM integration. Retain the agreed boundary: static worker for structural MP3 inspection; no full renderer-worker/WebGL rewrite without a demonstrated bottleneck and separate compatibility design. The displayed Phaser renderer is configured opaque; the detached board’s native exports report `willReadFrequently: false` in both engines and `alpha: true` in Chromium (alpha unavailable in WebKit). No canvas-attribute change is justified by these observations. [Worker example](https://web.dev/articles/offscreen-canvas), [Phaser renderer](https://docs.phaser.io/api-documentation/class/renderer-canvas-canvasrenderer).
- **Sustained heat needs hidden-work and background checks.** WebKit recommends minimizing hidden animation and unnecessary activity. Keep title/Demo/background owners in the sustained investigation; a short desktop speed-up is insufficient evidence of reduced heat or battery demand. [WebKit power guidance](https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/).
- **Record deployment and scheduling conditions.** WebKit maintainers confirm additional iOS 27 hardening for plaintext HTTP navigation. The user has confirmed published HTTPS play, so that plaintext-HTTP condition is excluded for the reported iPhone slowdown. Manual diagnostics now retain protocol and secure-context state without the full URL. Record browser/OS, regular Safari versus PWA, viewport, observed callback cadence, display/power settings, temperature and audio. Leave browser security settings unchanged. A refresh-rate proposal is not proof of the cadence actually delivered. [WebKit HTTP report](https://bugs.webkit.org/show_bug.cgi?id=324968), [frame-rate explainer](https://webkit.github.io/explainers/animation-frame-rate/).
- **Keep ordinary misses and task boundaries visible.** Long Animation Frames starts above 50 ms and cannot replace raw 20–40 ms cadence evidence. A resolved promise does not create a rendering opportunity. Yield only nonauthoritative preparation where justified, while keeping simulation ticks and durable saves intact. [Long-frame API](https://developer.chrome.com/docs/web-platform/long-animation-frames), [task examples](https://web.dev/articles/optimize-long-tasks).
- **Retain startup, worst interruptions and sustained behavior together.** WebKit's March 2026 JetStream 3 example measures first, worst and average iterations and explains why small isolated benchmarks can reward changes that miss real workloads. Apply that measurement principle to the game's existing phase summaries; it does not imply changing this JavaScript game to WebAssembly or using a benchmark score as a gameplay gate. [JetStream 3 example](https://webkit.org/blog/17899/introducing-the-jetstream-3-benchmark-suite/).
- **Distinguish the graphics environment from the game.** Chromium documents environment-dependent headless GPU support. The retained Linux profiles identify the browser and CPU stress but do not observe the active graphics backend. Record that backend when available before future diagnostic runs, and retain unavailable status otherwise. Do not silently enable GPU flags, change security settings or relabel historical rows; actual Canvas2D settings alone do not prove hardware acceleration. [Chromium headless GPU documentation](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/gpu/using-gpu-hardware-in-headless-chrome.md).

Further research examples refine the remaining investigation:

- **Bind font readiness to the final layout.** The CSS Font Loading specification says `FontFaceSet.ready` settles after relevant layout and font-loading work, but further document changes can require more fonts and replace the ready promise. Its canvas example explicitly loads the selected font before drawing. Keep the existing selected-font owner, settle the eventual play layout while paused, and recheck prepared geometry before activation. A prior fulfilled promise does not prove a later layout is ready or physically displayed. The native cancellation successor must retain both observed requests for the same font under one bounded owner. [W3C specification and canvas example](https://www.w3.org/TR/css-font-loading/).
- **Prepare the eventual play layout before granting play.** WebKit's ResizeObserver example delivers size changes as part of rendering and can perform another layout after an observer changes geometry. A public Start/Resume host control now demonstrates a source gap: readiness can be accepted at paused-screen dimensions, then running-only handheld CSS changes the displayed board dimensions and invalidates preparation after play begins. The control models size delivery and does not measure native layout cost or explain the retained WebKit interruption. Apply the final presentation geometry while still paused, account for its size change, and complete the existing prepared submission and quiet cadence before granting play. Preserve cancellation, the authoritative flight state and the original interruption boundary. [WebKit ResizeObserver example](https://webkit.org/blog/9997/resizeobserver-in-webkit/), [layout and interaction latency](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing).
- **Inspect actual canvas commands and surface dimensions.** WebKit's Canvas debugger can record/replay drawing commands and expose per-canvas dimensions and memory; its example reveals unnecessary drawing outside the visible area. Use a short separate diagnostic capture to identify redundant work when available. The older web.dev canvas example warns that oversized cached surfaces can erase pre-rendering gains; it is a hypothesis to measure on current browsers, not evidence for changing coordinates, reducing artwork resolution or adding more layers. [WebKit canvas example](https://webkit.org/blog/8452/canvas-debugging/), [canvas caching tradeoff](https://web.dev/articles/canvas-performance).
- **Keep diagnostic capture separate from timing.** WebKit documents that its Media & Animations timeline can itself affect performance and that the Screenshots timeline captures every composite. Run these only in separately declared diagnostic observations. The current PRE_STEP→POST_RENDER measurement already includes synchronous Phaser submission; browser compositor/raster execution and the cause of an interval cannot be inferred from that number alone. [Web Inspector timelines](https://webkit.org/web-inspector/timelines-tab/).

- **Do not equate low blocking time with smooth delivery.** Chrome’s example distinguishes animation-frame duration from input-blocking duration: several shorter tasks can collectively delay rendering, and low blocking time can coexist with visible animation delay. Keep raw cadence and the unchanged gameplay gates alongside application work; a favorable responsiveness number cannot clear the uneven WebKit population. [Long-frame timing example](https://developer.chrome.com/docs/web-platform/long-animation-frames).
- **Promote a joined request without duplicating it.** The task-scheduling explainer separates cancellation from changing priority, and explicitly leaves fetch priority outside that API's scope. Apply the principle within the existing media owners: a demanded cue can promote its live prewarm and its remaining stages, preserving its original deadline and native decode reservation. Cancelled work stays cancelled. This fixes the demonstrated repeat-read path without adding a browser scheduling dependency or claiming control over native decoder priority. [Priority/cancellation example](https://github.com/WICG/scheduling-apis/blob/main/explainers/prioritized-post-task.md), [Web Audio decoding algorithm](https://www.w3.org/TR/webaudio-1.0/#dom-baseaudiocontext-decodeaudiodata).
- **Confirm device versions directly and detect measurement APIs.** Safari 26.2 added Event Timing and changed the reported iOS user-agent version to a frozen value. Record the device's actual OS/browser versions from its settings; do not infer them from the exported user agent. Where available, Event Timing can supplement discrete Start/Resume interaction diagnosis, but it cannot replace continuous movement/gamepad submission measurements or explain every frame gap. The older automated WebKit build's missing APIs remain unobserved; no new observer is added to ordinary timing runs. [WebKit release notes](https://webkit.org/blog/17640/webkit-features-for-safari-26-2/).

- **Check that the measurement can resolve the target before repeating it.** Normal browser timers may be coarsened or jittered. With the unchanged ten-pair analysis, even equal 6.3 ms p95 arms and a 0.1 ms error allowance give a +5.73% upper sensitivity term before sample variation. Preserve the 5% gate as unresolved where the declared method cannot establish it; do not change security settings or add artificial workload to obtain a pass. [Source-bound calculation](solo-overhead-resolution-review-20261017.md), [W3C timing model](https://www.w3.org/TR/hr-time-3/#dfn-coarsen-time).

## Unchanged acceptance gates

Let **B** be the foreground callback interval established during lightweight preparation and recorded before loaded play.

| Measurement                            | Gate                                                                                      |
| -------------------------------------- | ----------------------------------------------------------------------------------------- |
| Application update/draw/HUD work       | p95 ≤ `min(10 ms, 0.6 × B)`                                                               |
| Callback cadence                       | p95 ≤ `1.2 × B`; p99 ≤ `2 × B`                                                            |
| Missed opportunities                   | ≤1% in qualified active windows; investigate every consecutive burst                      |
| Application input-to-render submission | p95 ≤ `2 × B`; not physical input-to-photon latency                                       |
| Severe interruption                    | No reproducible application-caused ≥100 ms foreground stall or overload pause             |
| Retained resources                     | Explicit limits and stable retention across completed transitions                         |
| Diagnostics overhead                   | ≤5% p95 application-work increase in matched enabled/disabled runs, including uncertainty |

Retain every >33/50/100/250 ms interval and investigate active tasks over 50 ms. Keep synthetic 30/40/45/60/90/120/144 Hz schedules and cadence changes; 100/249/250/251/500 ms interruptions; neutral Resume; controller disconnects/discrete catch-up edges; ownership/cancellation/fallback faults; identical-coverage layout differences; and public save/replay identity checks. Fault injection is separate from performance-pass runs.

Completion requires demonstrated removal of application-caused stalls within declared scenarios, compatible visuals/saves/replays, bounded ownership and successful delivery checks. It does not establish immunity to browser scheduling, driver failures or thermal throttling. Physical-device gates remain explicitly open until observed.
