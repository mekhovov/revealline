The executable harness separates three kinds of evidence: native performance observations, repeated public-UI lifecycle transitions, and synthetic recovery-handler checks. Fixed-step route preparation is recorded as model correctness. None of these substitutes for the iPhone 17 Pro Safari or Steam Deck OLED Chrome check.

Create a new fixture directory with `node scripts/prepare-solo-qualification.mjs <new-directory>`. The preparer replays existing legal routes, verifies their public replay, and rejects missing required mechanics. It writes validated Playground imports and runnable `.qualification.json` cases. It does not edit a player profile, gameplay definition, archive or runtime.

Native replay correctness is checked after the gameplay browser and context close. A fresh instance of the same engine must report exactly the same full `browser.version()`. It visits only the observed build's `build-info.json`, requires identical metadata bytes/source revision and production CSP, then imports that artifact's strict replay, core and mechanic-view modules. A dependency-free shared inspector verifies the unchanged checkpoints before reconstructing mechanic counts. Module hashes and every failure are retained; no reviewed-demo exception or rewritten enemy checkpoint is allowed. This separate verification is excluded from gameplay timing. Node reconstruction remains a separately labeled portability result: native trigonometry can produce a different enemy checkpoint across engines, so a Node mismatch cannot replace the strict same-engine result. Missing identity, changed browser version, native mismatch or missing required mechanics fails the scenario. Old failed reports are never relabeled after a supplementary diagnostic succeeds.

Consecutive-rAF observations begin at the second callback. The first frame timestamp, actual callback time and registration-to-callback delay are separate fields, because a frame timestamp can precede observer registration. Historical reports through tooling `2939bc0cc` may contain one negative boot interval from subtracting registration time from that timestamp; retain those reports and exclude that boot-only artifact from interpretation. Later lifecycle intervals are neither clamped nor removed. Application scene timing is unchanged.

Retain failed routes and their partial external measurements instead of selecting only completed attempts. A route that fails differently cannot qualify the full requested workload on that build.

The shared independent probe measures Phaser `PRE_STEP` through `POST_RENDER`, including render submission and observer overhead. After boot with an actual visible enabled public launch, it captures thirty foreground, non-playing rAF intervals with a five-second deadline. Packaged releases intentionally defer the mission picture to Start; their window is labeled “prelaunch title; required preparation deferred” and picture readiness remains false. This measures display cadence, not application readiness. Other routes require observable picture readiness. The fixed median B is admitted only when the coefficient of variation is ≤0.10 and p05–p95 spread is ≤20% of B; otherwise calibration remains provisional. Raw samples, variance, visibility, phase, picture state and launch controls are retained, including readiness timeouts. Optional catalogue/decode work can still be present, so the window does not prove quiescence. The work probe attaches before this window and retains subsequent preparation costs. The runner never recalibrates during play or warms assets by starting an extra run. The warm public-reload recipe warms eligible document/runtime resources; it does not establish cached mission originals when their first preparation is still deferred. Independent work/cadence/missed-frame gates remain separate from missing baseline internal latency, safety and owned-resource counters. Exact work quantiles are reported only when the bounded5,000-callback ring retained the entire document's observations; otherwise only histogram bounds are available. Baseline `partial-baseline-internal-unknown` is not a complete performance pass. The headline aggregates every requested internal/external gate: failures, required review and inconclusive components remain explicit, with all unresolved component rows retained.

`--server-fixture-access` unlocks the local preview server's fixture password without adding browser routing. With the server's revalidation cache policy this preserves normal HTTP cache behavior. `--fixture-access` instead rewrites the HTML access metadata with Playwright routing; that disables HTTP cache and is explicitly labeled. Neither changes CSP. Service workers are blocked in this runner; offline install/update testing remains separate.

To exercise the catalogue's real same-origin policy, optionally use `--public-url=https://mekhovov.github.io/revealline/game/ --manifest=/absolute/path/to/frozen/manifest.json` while the positional URL remains the local generated build. The browser retains the original production origin and exact CSP. Every manifest-admitted deployment path uses local transport, including `authoring/` dependencies outside `game/`. Missing deployment paths are blocked instead of falling through to today's public runtime. Only the explicit sibling `/revealline-soundtracks/` publication may remain live on that origin. The manifest revision and hash are recorded. This is synthetic network/origin qualification and disables HTTP cache; it does not establish deployed network latency. No security-disabling browser flag or CSP weakening is used.

The practice cases import scenario files through the public Playground file control, launch its ordinary preview, and follow the prepared full-preview link. Original-art cases launch their public Journey or pack directly. The runner never writes IndexedDB, localStorage, sessionStorage, run objects, simulation ticks, or caches. Authored gameplay definitions stay unchanged; prepared practice fixtures omit authored decorative backdrops and cannot qualify original-art decode/memory pressure. After gameplay, mechanic cases export the actual recording through More → Workshop tools → Export replay. Only after the browser closes does the harness verify and reconstruct that recording, counting actual captures, erosion, shots and jamming. Requested coverage is separate from this proof; a missed feature fails the scenario.

`scenarioStatus` describes public actions, actual outcomes, replay mechanics and declared resource checks. `performanceGateStatus` is separate. The evaluator uses the final paused application export and its measured pre-play cadence B. It checks playing-work p95 ≤ min(10 ms, 0.6B), cadence p95 ≤ 1.2B and p99 ≤ 2B, missed opportunities / (observed + missed) ≤ 1%, and keyboard input-to-submitted-render p95 ≤ 2B. It requires at least 100 playing frames and 20 keyboard samples for those respective checks. Missing calibration or samples remain unobserved; a quantile bucket crossing its threshold is inconclusive. These minimum counts are safeguards against tiny passes, not statistical confidence. At least three independent runs per scenario/browser/quality are still needed.

A numerical pass means only `pass-observed-window`. Interruption/failure counters must be zero. Any prior-playing-phase interval ≥100 ms, playing work >50 ms, or burst exceeding two missed opportunities requires attribution before qualification. Transition-crossing intervals remain in the report; a pause transition is not silently deleted or declared an application stall. Physical devices, thermal stability, resources, actual mechanics and matched diagnostics overhead remain separate. The runner does not establish a ≤5% overhead bound; use the paired diagnostics tool and retain inconclusive results. Recovery cases are explicitly excluded from numerical performance qualification. Exit code 1 denotes a scenario/replay failure; 2 denotes failed numerical gates or invalid numerical evidence after a successful scenario. Exit 0 may still contain inconclusive or review-required gates: inspect the JSON, not just the process exit.

Each snapshot requires a paused/result boundary. Counter comparisons use a named group of compatible snapshots and explicit paths; missing counters are unobserved, not zero. Owned categories may share underlying assets, so the harness does not sum them into total browser memory. Forced GC, heap snapshots, `Memory.prepareForLeakDetection`, screenshots and pixel readbacks are excluded from timing. The rAF histogram reports bounded quantiles and retains transition-crossing severe intervals. Native audio starts prove API activity, not physical speaker output.

For separate recorded-audio correctness, run a prepared speech or imported-music scenario with `--audio-proof`. The same scenario without this flag remains the ordinary performance run. Proof mode copies and hashes at most 2 MiB per encoded recording, 16 MiB in aggregate and 64 identities; it never reads PCM samples. A speech requirement passes only when an exact original-file hash is linked to a successful native buffer start during running, picture or result presentation. A decoded cache entry, enabled preference or paused preview alone cannot pass. `audio-ready` waits for exact decoded recordings only in proof mode; ordinary timing uses the declared fixed preparation wait, whose recording readiness remains unobserved.

Imported music proof links each playable `audio/*` Blob URL to its original encoded hash, requires native playback and continuous chronological advancement of `currentTime`, and retains first-track order. Seek, reset, pause and implausible time jumps end an advancement segment; backwards resets cannot satisfy the requirement. The start/end witness is retained separately from natural-transition evidence. A labeled `natural-music-transition` duration wait contains no harness input. Within that window, a switch to the other known recording requires the outgoing track to be within four seconds of its duration or to have emitted native `ended`; this admits the player's near-end crossfade. All timestamps and supporting events are retained. Events are bounded to 512, buffer starts to 128 and retained media elements to eight; missing, pending or capped identities remain unobserved and fail an explicitly requested proof. The whole proof run is excluded from timing and memory qualification, and cannot be combined with `--memory-profile`. Hashing and retained elements perturb both. API starts and advancing media do not establish audible output at the speakers.

The imported-music scenario uses ordinary listening mode through the public Filters control. The original bundle's recording-mode refusal is preserved: its unchanged metadata does not establish the additional gameplay-video permissions. After import and filter saves, the recipe waits for an enabled public selection button, chooses the exact playlist, supplies a fresh Play gesture, and retains the visible current/next titles. These controls do not replace the exact native playback proof.

The public `result` action waits for the visible won/lost overlay and uses only available Skip celebration / Show result buttons, with a bounded deadline. It does not advance clocks or assign the result. This avoids assuming that celebration controls appear within a fixed short delay.

For a separate Chromium memory run, add `--memory-profile` to `twenty-retries` or `ten-next`. It summarizes the last ten same-group post-GC checkpoints, reporting values, range and first-to-last change. Missing optional native counters remain unavailable. It never calls `Memory.prepareForLeakDetection`, which would retire workers and caches. Chromium JS/embedder/backing-store counters are not total process, native audio decoder or GPU memory.

## Accepted workload and failed-attempt evidence

Every prepared recipe declares `expectedReplayDefinition`: the complete immutable level, including its rules, geometry, actors and revision, plus the explicitly selected run options. The native runner requires this declaration and a public replay export. Strict same-engine verification compares every declared field after accepting the unchanged recording. A matching title or mechanic count cannot compensate for different rules or a different mission. Undeclared run options are not claimed equal. Lifecycle recipes without an existing export add one after their final paused/result snapshot; the long-recording recipe deliberately exports its unfinished pre-win recording.

Tool uploads wait for an enabled public control outside inert, hidden or busy ancestors. For Playground imports, it also waits for the explicit loading indicator to be hidden, retains the public status and handler/file-selection observations, and opens the existing Level JSON disclosure and compares its parsed contents with every submitted level field before Preview. A bounded read-only witness retains native input/change events and retires its listeners immediately after upload; it does not replace application handlers. Visibility alone is insufficient: the input is already present during asynchronous tool boot, before its change handler is attached. The hidden loading indicator can also follow a caught initialization error, so its status is not proof of successful import. This check does not write application state or bypass validation. The independent native replay definition check is still required.

On scenario failure, the runner attempts a public pause and retains the partial HUD, diagnostics and resources. If ordinary enabled controls offer a replay, it exports the exact bytes and verifies that partial play separately. The original failure remains failed even if the partial recording is valid. Partial mechanic counts do not satisfy the completed scenario's requirements. Previous reports without failure-time recordings remain unchanged.

## Bounded CPU profiling

Use `--cpu-profile` only for a separate Chromium diagnostic run. It cannot be combined with `--audio-proof` or `--memory-profile`, and the scenario timeout must be at most 300,000 ms. A recipe declaring `requiredProfile: "cpu"` refuses to execute without that flag. The entire run is excluded from timing gates.

The duration limit schedules a stop request; event-loop delay and bounded CDP response time can extend the recorded span. Actual timestamps and sampling duration remain in the receipt rather than claiming an exact wall-clock cutoff.

The existing CDP session records a 1,000-microsecond sampling interval from before navigation through the last action, including menus, preparation, Pause/save, replay export and Next. The owner stops once, also attempting to retain a partial profile on scenario failure. Its duration cap stops profiling and closes the observed context; hitting the cap remains a failed diagnostic attempt. The separate immutable `.cpuprofile` file has a SHA-256, byte count, timestamps, sample count and explicit microsecond clock fields in the report. Failure to retrieve or save it remains visible. Worker, native decoder and GPU work are not fully represented by this main-thread profile.

`long-recording-save-reward` is a separately profiled recipe: 180 seconds of legal neutral input on original First Return, public Pause/save and export, then Resume, an earned win, immediate Next and ten seconds of new gameplay. The strict exported replay covers the long unfinished flight before the win. Public outcomes and the CPU profile supply separate evidence for the later transitions; no winning replay, durable-save success, active reward overlap or performance pass is inferred merely from the recipe.
