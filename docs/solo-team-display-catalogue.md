# Solo browsing of Team missions

This F10 implementation slice replaces primary Solo's synchronous remote-Team
display construction with three bounded, hash-verified display files. Receiving
Team still creates and validates its own executable mission and selected preset.
No sender display object acquires native row, pack, route, replay or progression
authority. F10 as a whole remains partial; lessons and the other browsing hosts
remain separate work.

## Authoring and distribution ownership

The existing fixed PR1771 authoring workflow produces and checks all three targets
in fresh guarded processes. The additive parity checks compare each fresh output
byte-for-byte with its committed runtime file and compare registry edition,
factory, project identity, length and SHA-256. Every native mission/preset, live
English/Ukrainian detail and full expanded diagram is compared with the adapter.
All previous authoring and native ownership assertions remain.

To update the files, use the existing fixed guarded authoring workflow, review its
actual output and receipt, then replace the three runtime files and corresponding
code-owned descriptors together. The deterministic descriptors contain schema
target, exact source identity and content hash, not a whole-main commit,
translation hash, build timestamp, local path or native trust token. A source
change that alters the projection must fail parity until the reviewed data is
updated. Locale-only text stays behind live message references.

The existing build `game` include copies these modules and JSON files. Existing
runtime-directory offline policy retains all three files: 669,955 bytes before
archive/compression and manifest overhead. Existing package construction must
measure the final cache/file limits; the size here is not a completed package
measurement. The new source-only adapter joins the existing published-Solo
boundary list, so a packaged Solo route does not gain unused native Team imports.
Published Solo's existing display views and launch owners are unchanged.

The existing build computes content hashes, build identity, cache revision and
service-worker cache file metadata from final entries. Do not manually edit
generated service-worker, cache or readiness files. A cached display catalogue
does not prove the receiving Team executable route or artwork is installed.
Missing files remain explicit failures; installed and optional-content readiness
owners are unchanged. No actual iPhone or Steam Deck hardware is available.
