# Field Kit production and adoption

The production pipeline connects the original sources, prepared assets, runtime and local Asset Studio. It is presentation data: campaign definitions, checkpoints, difficulty, collision geometry and earned picture identities remain separate.

`node scripts/produce-field-kit-theme.mjs --write` assembles the pinned fonts, prepared title scenes, native pixel sprites, semantic glyphs and prepared reveal images into `game/presentation/compiled/`. `--check` reproduces those files and checks their bytes. The generic compiler also accepts a validated `.rltheme` bundle; neither a browser upload nor a source generation changes the deployed game.

The compiler emits a closed `runtime.json` snapshot, a complete editable `studio.json`, shared CSS, hash-addressed asset files and their inventory. Runtime asset URLs derive from hashes and MIME types; uploaded data cannot choose arbitrary fetch paths or executable recipes. The studio document retains unselected immutable history, so a release collection can be edited and exported without dropping its prior file revisions. The presentation manifest limit is 4 MiB: the original 2 MiB limit could not retain the complete production collection plus immutable review successors. The presentation transfer limit remains 32 MiB; player-media metadata and storage limits remain unchanged.

Production adoption stages the complete output before switching directories. It replaces only files already accounted for by a valid compiler ownership manifest. Unlisted files, edited bytes and symlinks stop regeneration and remain intact. Reproduction checks compare the complete file set as well as every body, so obsolete or unexpected assets cannot silently inflate a release.

`authoring/library/fpv-field-kit/production.rltheme` is the durable production ledger. Regeneration reads its complete verified history and retains old file bytes. Unchanged assets keep their exact revision; a changed drawing, geometry, source recipe or prompt gets the next revision with its prior revision as parent. Recording a review also creates a successor. Reproduction preserves an existing review when its underlying content is unchanged and invalidates it when content changes. An explicit reset may bind a prior revision without deleting later history. Component provenance includes a digest of its actual source files. Slot-contract changes require an explicit compatible migration rather than silently rewriting a v1 slot.

Production inputs are deliberately separate:

- `game/assets/field-kit/sprites/sprites.json`: 30 original native pixel drawings, geometry, measured bounds, source hashes and complete prompts. Motor hubs remain static; the renderer supplies propellers.
- `game/presentation/icons.mjs`: 45 original semantic pixel glyph recipes. The compiler generates their PNG bytes once at the registered dimensions.
- `authoring/library/fpv-field-kit/prepared-scenes-v2.json`: exact landscape/portrait title derivatives on the reveal palette and 3× pixel grid; the original files and v1 derivatives remain unchanged in history.
- `authoring/library/fpv-field-kit/prepared/reveals/reveals.json`: each prepared reveal frame and every exact owner binding, full effective prompt, original hash, palette and preparation operation. Larger generated originals remain in the authoring library and are not duplicated in player downloads.
- `game/ui/fonts/field-kit/provenance.json`: pinned upstream source, licenses, actual WOFF2 hashes and variation axes. Handjet uses 600; Exo 2 uses 400–600; Plex Mono uses 500. The interface keeps its local Plex symbol fallback.

New scene derivatives use an explicitly recorded nearest-grid and fixed-palette preparation process. They are generated illustrations prepared into deliberate integer clusters, not claimed to be hand-painted native-grid originals. Their original PNGs remain unchanged. The full composition plan has 38 subjects, 44 exact frame exports and 56 current FPV picture owners; the prepared manifest reports missing compositions until each exists. Shared subjects do not imply shared saved-picture identities.

Source, produced and reviewed stages are evidence states. A structurally valid recipe is still source-stage until its actual component and relevant states are reviewed. A generated or prepared image is produced-stage until its native size, gallery scale and real board context have been inspected. Compilation never marks candidates reviewed automatically.

On a fresh studio workspace, the release collection loads from the fixed compiler output. An existing local workspace remains intact; **Load release collection** stages a namespaced collection that can be saved or undone. Hashes, headers, exact file lengths and the total byte budget are verified before any candidate is returned. A failed or cancelled load leaves the existing workspace alone. Player saves and the media database are not accessed by this studio loader. Collection imports reuse revisions only when their original identity and full metadata match, including resolved derivative parents. New or conflicting records receive namespaced identities; a child of a conflicting parent follows the imported parent. This keeps a full exported collection importable into its own workspace without duplicating all immutable history.

AI briefs include the selected asset's actual file revision, current pivot/anchors/frame, effective production prompt, shared tokens and baseline slot contract. Edited geometry takes precedence over baseline geometry for an edit request. Collection briefs include each selected member's current geometry and production brief. Preserve these requirements when producing variations; the prompt alone is not validation evidence.

Geometry editing follows actual renderer support. Actors, terrain and pickups can change visual pivots without changing gameplay centers. Rotor anchors belong to actor bodies; nine-slice regions belong to registered frame components. Interface glyphs, backgrounds and complete reveal pictures use centered placement. Unsupported controls are locked in the studio and rejected at the binding boundary; occupied bounds remain inspection metadata.

Runtime picture adoption is described in [the presentation host contract](presentation-runtime.md). New defaults become durable exact still-media revisions only for eligible new attempts. Existing saved/earned pins, explicit legacy choices and manual artwork remain authoritative. Collection and mission thumbnails must follow the earned picture receipt rather than assume the current source background.

Every public release still needs its exact-source gates, immutable source/artifact identity, Pages byte verification and actual play. Source previews and desktop emulation do not certify physical touch/controller devices or public offline delivery.

## Final source review

The Phase 7 evidence records exact asset revisions and source-code/file hashes, agent visual decisions, observed native state/return-focus checks, glyph results and bounded renderer measurements. Reviewed successors are appended only after their corresponding explicit decisions; structural compilation is not a visual approval. The 194 required FPV slots are distinct from 99 optional historical source-adapter slots. Old originals and immutable metadata remain retained. Public delivery, offline journeys and physical-device limits have their own receipts.

Sequential reveal corrections are recorded in `reveal-source-revisions.json`. The preparer verifies every source in the chain, rejects stale or forked predecessors and writes a distinct versioned derivative. Signal 06v2 is selected for new eligible attempts; its v1 original and export remain in history. Font/audio briefs request actual files in their medium while retaining current custom production requirements.

Before freezing a new production release, run `node scripts/check-field-kit-readiness.mjs` after committing and reproducing the collection. It requires reviewed declarations with nonblank evidence for all selected required slots and binds the result to the committed ledger/source identities. Optional historical sources may remain. An older reviewed revision cannot qualify a newly selected unreviewed successor. This mechanical check does not replace native visual review.

The combined actor library and redesign keep the existing 64 MiB offline-core ceiling by declaring `fpv-arcade-r5.json` optional, alongside earlier Arcade editions and Pressure Frontier. Its original bytes remain in the loose distribution, ZIP and manifest. The existing game-data message names optional chapters and instructs installation while online; installed packs stay in device storage for offline play. Base missions and normal saved-flight storage are unchanged. The built cache and an installed Arcade R5 offline journey require explicit release verification.
