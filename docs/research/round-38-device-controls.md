# Device controls and entry: v0.29 research

Reviewed 2026-09-13. This is a source inspection and product recommendation, not browser or physical-device acceptance. The parent task reported a `file://` screenshot with an incorrect D-pad and a legacy failure page; this reviewer did not view that screenshot. The inspected starting HEAD was `5f04aede1e927c9ecec59b4ed1d75a18c3d8c83f`; v0.29 implementation is proceeding concurrently. File references describe the inspected boundaries, not an assertion that the final implementation retains these defects.

The recommended change is a consistent entry shell and a contextual input presentation layer. Keep the existing deliberate movement, pause, recovery and replay boundaries. Screen size chooses layout; input capability and actual use choose the controls shown. The user's requirement to remove the bottom action toolbar is a product choice, not a platform certification requirement.

## Confirmed source traps

1. **The D-pad relies on a removed grid item.** In [style.css](../../game/style.css), Left and Right specify only row 2; the hidden `#stop-button` in [index.html](../../game/index.html) no longer occupies the center. Auto-placement therefore puts Right in column 2. Assign all four coordinates explicitly: Up (2,1), Left (1,2), Right (3,2), Down (2,3). The empty center is not a Stop target.
2. **The old presentation survives unsuccessful initialization.** `attachGameShell` adds `.game-shell` late, after content/storage/painter work in [app.mjs](../../game/app.mjs). Static HTML includes the old deck, D-pad, version placeholder and flight copy. The runtime catch changes the old overlay; `finally` removes startup inertness even after failure. Static module-import failure happens before that module's `try/catch` executes. A failure of an early module and a failure inside initialization need separate handling; the screenshot alone does not establish which occurred.
3. **Controls are partly hidden by viewport, not input.** [pixel-theme.css](../../game/ui/pixel-theme.css) hides the D-pad only for fine/hover pointers at widths of at least 681 px and only after `.game-shell` exists. A small desktop can retain it; a coarse device with controller can retain it. The bottom actions/utilities remain. The older short-landscape grid also reserves a 144 px controls column. Hiding buttons without removing that reservation wastes board area.
4. **Capability and active input already have different meanings.** Initial `body.dataset.inputMode` uses `maxTouchPoints` or `any-pointer: coarse`. Native keyboard/pointer events and controller samples then replace it. [controller-navigation.mjs](../../game/ui/controller-navigation.mjs) receives native input even outside menus. A replacement policy must not turn mere controller connection, idle axis noise, pointer movement or synthetic compatibility events into a new flight command.
5. **The input adapter owns the original nodes.** [input.mjs](../../game/ui/input.mjs) captures `[data-move]`, Boost and action elements when attached. Moving those nodes preserves listeners; replacing them or cloning duplicate IDs does not. Pointer capture, keyboard activation and assistive click handling have different paths. An overlay must preserve those paths and avoid a page-sized input interception layer.
6. **Equipment copy is inconsistent.** Static HTML says Scan, but `updateLoadout` replaces the action label with the craft name. Supply is visible even for Scout's zero-capacity loadout. The general Help still says every field-enemy line contact costs a life, while a level with `classic.lineImpact` allows the travelling-front escape interval. Derive current-edition copy from the selected recipe/descriptor.

## Proposed presentation contract

| Context                                                         | Controls shown                                                                                                          | Input and focus contract                                                                                                                                                                                                                                                                             |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Desktop keyboard/mouse, any window width                        | Board/HUD and a compact top menu/pause affordance; no bottom flight toolbar or D-pad                                    | Keyboard remains a full game/menu path. Show current mapped key hints in briefing/Help, not permanently under the board.                                                                                                                                                                             |
| Assigned physical controller, including a phone/tablet          | Board/HUD, controller-specific contextual prompts, no touch pad by default after deliberate controller use              | Connection alone never starts a mission. Maintain neutral join/disconnect gates. A real touch can bring touch presentation back.                                                                                                                                                                     |
| Touch play                                                      | Four-direction pad near the left thumb and only the current edition's relevant touch actions; accessible top pause/menu | Visible only while gameplay owns input. Use stable thumb gutters around the actual board; transparent art does not make a hit target harmless. Never cover threats, the player, live trail or reconnect edge. On very short displays reduce/fit the board or use side gutters before overlapping it. |
| Ready, paused, loading a save, menu/reader, won/lost or picture | Contextual Start/Resume/Retry/Next/Back/Skip controls as applicable                                                     | No live touch steering surface. Focus and controller candidates are limited to the active surface; dialog editing/reading remains native.                                                                                                                                                            |
| Recovery or capture stop                                        | Appropriate status; no residual held action                                                                             | The host's existing per-substep reset requires a fresh direction after recovery or `capture.stopped`. Do not display a new instruction as if the old held key were fresh.                                                                                                                            |

Use an `auto` presentation policy with separate facts for touch capability, active modality and interaction scope. Initially choose touch when it is the available primary mechanism; otherwise choose keyboard/pointer. Change from deliberate input edges, not screen width or continuous polling. Keep other supported adapters live on hybrid devices. If an explicit touch-controls override is offered, make it a presentation preference, not a new movement ruleset.

For an active touch gesture, defer hiding/moving its control until release, or release physical captures/Boost through the existing lifecycle boundary. Do not call the logical-direction reset just because the layout or prompt changed. Pause preserves intent and the queued Grid turn; explicit Resume/Load continues that direction with the existing first-tick action/Boost neutral gate. Focus return alone does not resume. The host deliberately clears logical intent for new attempts, recovery and capture stop.

For the new Arcade edition, the parallel `arcadeActions` work is intended to disable manual equipment in the versioned rules. Omit Scan/Supply/Boost for that edition and explain movement/capture/automatic field pickups. Existing editions with manual equipment retain their authored rules and an appropriate input path. Hiding a toolbar is not sufficient to disable keyboard/controller actions in a new rules edition, and old replays must not be reinterpreted.

## Accurate explanations to use

These are inspected behavior facts from [abilities.mjs](../../game/core/abilities.mjs), [registry.mjs](../../game/core/registry.mjs), [systems.mjs](../../game/core/systems.mjs), [render.mjs](../../game/ui/render.mjs) and the host. They describe manual-equipment editions; do not promise them in movement-only Arcade.

| Topic       | Short explanation and qualification                                                                                                                                                                                                                                                                                                                                        |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Movement    | Tap a direction once to keep moving; a new direction changes heading. Immediate turns act immediately; Grid turns queue to the next grid center. Releasing or pressing the same direction does not stop. Only editions with `rules.stopOnCapture` stop when a cut closes; simply travelling on safe ground is not the same event. Pause is the universal deliberate break. |
| Scout Scan  | Reveals hidden objectives within the recipe's radius permanently and briefly displays moving bouncers' direction hints. It does not damage or slow enemies, capture terrain, or make the craft safe. Default Scout duration is 4 seconds and cooldown 6 seconds; use the actual recipe for other loadouts.                                                                 |
| Supply      | At a supply pad, refill charges for a charge-based craft. Scout has no charges to refill. This manual action is separate from Classic field pickups, which are collected by touching them.                                                                                                                                                                                 |
| Boost       | Multiplies movement speed while active, unless the current signal field blocks it. Use the authored multiplier. It grants no invulnerability. Keyboard is held; on-screen and solo-controller Hold/Toggle choices have their own existing settings.                                                                                                                        |
| Mission     | Reach the authored reveal target and capture every required objective; encounter/challenge rules can add requirements. Closing a line alone is not a level win. Use [missionBriefing](../../game/mission-brief.mjs) and the actual rules, including R3 impact timing.                                                                                                      |
| Progression | A win retains its picture/result and opens the next available mission according to campaign access. Standard/Gentle share mission and appearance access while retaining separate scores/medals; optional equipment seals require Standard. Practice does not award campaign progress. Retry starts a fresh attempt; Load/Resume preserves the saved one.                   |

Put the goal, one movement sentence and current threat rule on the briefing. Keep detailed equipment and progression explanations in the existing optional guide/Help. Reuse the actual binding labels. Keep dynamic cooldown/charges as readable status if manual equipment is relevant; temporarily unavailable actions should not make targets jump beneath a finger.

## Entry contract and bounded acceptance

Render a static dark loading/entry surface before module evaluation. Do not expose a playable-looking legacy page while loading. A small entry layer can own module-load rejection and content bootstrap failure; gameplay should become interactive only after its own readiness signal. Keep failure controls outside the inert gameplay subtree. Offer Retry for a retryable supported-origin load, a public Play link for a raw local file, and concise local launch instructions. Do not claim automatic save transfer between origins or clear storage on failure.

The existing [desktop policy](../../platforms/desktop/policy.mjs) already uses `revealline://app` with a stable persistent partition and secure, fetch-capable custom scheme; service workers are deliberately disabled there. [iOS configuration](../../platforms/ios/capacitor.config.json) uses `capacitor://localhost`. Keep those hosts and their persistence boundaries. An inline error helper also has to respect desktop CSP (`script-src 'self'`); a file-only inline workaround must not become the sole native failure path.

Acceptance should cover these bounded cases without replay golden regeneration:

- A missing module, missing content JSON and raw-file entry all produce the modern recovery surface with no active old controls. A normal slow bootstrap becomes Ready only once. Verify the resulting error text, not a presumed browser failure cause.
- At 320 × 640, 390 × 844, 844 × 390, 844 × 501 and 1280 × 720, inspect both touch and non-touch presentation, Standard/Large text and safe areas. Non-touch widths never create a D-pad or empty control rail. Touch targets are at least 44 CSS px, have explicit cardinal placement, and do not obscure playable cells.
- On actual host input: keyboard → touch → controller → touch, disconnect while moving, rotate while Boost is held, and open/close a reader. Modality changes must not change the run identity, rules or replay checkpoint. Physical release must not erase persistent direction; menu activation must not leak into flight.
- Actual pause and saved-load continuation retains heading/queued Grid turn, while recovery/capture stop needs a fresh gesture. Start/Resume, Retry and Next stay distinct; held Confirm cannot cross them.
- Old manual-equipment and new movement-only editions display truthful controls and retain their separate core contracts. Test disabled-action replay semantics independently from hidden UI. Inspect progression and guide copy against real win/required-objective/Practice behavior.

No source changes, gameplay tests, browser bootstrap, screenshot measurements or physical-device tests were performed for this research. Those remain implementation acceptance work.
