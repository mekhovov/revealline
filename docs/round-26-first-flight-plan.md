# Round 26 — First Flight implementation plan

Prepared on 12 September 2026 after v0.15.0 preservation, for implementation review. **No runtime implementation is included in this document.** The accepted [candidate](round-26-candidate-backlog.md) becomes one optional, repeatable three-lesson course using the existing solo engine. It adds no campaign gate, paid reward, player preference or simulation/portable-format version.

## Existing behavior to preserve

[Watch first cut](../game/app.mjs) already demonstrates a real cut: its fixed-step `demo` branch supplies Down with Boost/ability/pickup off. Its handler prepares the first map, sets practice, starts explicitly and awards nothing. Retain this passive example outside the course; the new feature asks the player to perform the actions. The candidate's description of current learning tools should not be read as claiming that this demonstration is absent.

[How to play](../game/index.html) explains safe ground, closure, enemy-seeded fill, self-contact, border patrols and goals. Opening it calls `pause(true)`, which can autosave an unfinished ordinary flight. [Controller Lab](../game/controller-lab/lab.mjs) loads validated scenarios into the real app using the immutable practice context and a session-bound virtual pad. [Replay Theater](replay-theater.md) remains a separate read-only demonstration tool.

The course reuses ordinary level-v1/core-v2 movement, collisions, capture and recovery. It does not modify the existing 29 maps, classes, scoring, historic checkpoints or reward rules. The primary guidance and its limits remain in the candidate: XAG 109 supports repeatable participatory instruction; XAG 116 supports time to read UI, not removing existing gameplay deadlines. Human comprehension and enjoyment remain unmeasured.

## Three concrete lessons

All three are new, private training maps: 48×36, spawn `(24.5, 0.5)`, no walls, a home supply pad at spawn, seed 1, FPV presentation and the unchanged Scout recipe as the sole course loadout. Preserve First Signal's current rules: three lives, movement 10 cells/s, Boost multiplier 1.5, recovery/grace 0.7s, player radius 0.18, 10 points/cell and medal thresholds 40/73s. Other optional rules keep their normalized defaults; there is no mission deadline, cut deadline or cable cap. Internal score/time/medal values remain ordinary simulation data and are never saved as course rewards. Ability/Supply can remain visible with truthful descriptions; neither is required. Hangar/class changes are unavailable in this fixed lesson roster.

| Lesson ID / level ID                         | Exact authored content                                                                                                       | Participatory instruction                                                                                                                                                               |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `close-line` / `first-flight-close-line`     | One stationary bouncer at `(37.5,24.5)`, velocity `(0,0)`, radius 0.25. No objective; coverage 45%.                          | “Leave the marked safe edge. Keep going to the opposite edge to close your line.” Show the live-line status while cutting and the real reveal after closure.                            |
| `empty-side` / `first-flight-empty-side`     | Stationary bouncers at `(12.5,27.5)` and `(38.5,27.5)`, radius 0.25. Required visible `garden` at `(8.5,8.5)`; coverage 25%. | First fly down the center. Then move back along that secured line and turn left within the marked band, rows 16–24. The band permits a nine-cell timing range.                          |
| `picture-home` / `first-flight-picture-home` | One bouncer at `(38.5,27.5)`, velocity `(-1,0.7)`, radius 0.25. Same required `garden`; coverage 65%.                        | Reveal the marked objective and enough territory while a threat moves. Offer less route guidance. A failed cut is explained if it occurs, but causing a failure is never a requirement. |

Use short shape/label markers for the initial direction, safe divider, turn band and return edge. These decorations have no collision or fill authority, do not obscure enemies and have text equivalents in Mission brief. Use the existing original procedural picture/finale initially; this course does not claim three new illustrated rewards.

### Exact evidence, not a capture-size guess

Define a cell by integer `(x,y)` and index `48y+x`. For lesson 2:

- Divider `D = {(24,y) | 1 ≤ y ≤ 34}`.
- Horizontal line `H(h) = {(x,h) | 1 ≤ x ≤ 23}`, where `h` is any integer from 16 through 24.
- Northwest rectangle `R(h) = {(x,y) | 1 ≤ x ≤ 23, 1 ≤ y ≤ h}`.

Observe a pair of **owned before/after snapshots for one actual fixed step**, including tick/status, live-trail indices, cell ownership, relevant objectives/enemy centers and whitelisted public events. Bind the observer to the exact normalized lesson, ruleset, seed, policy, recipe/roster and fresh attempt ID. The app owns `runId` outside the core run, so it must explicitly pass that ID into every fact capture; the observer cannot derive attempt identity from a mutable run reference. Never read renderer colors, mutate the run or infer an action from a timer. Calls without an advanced tick do not grant progress.

1. Lesson 1 completes only after a real `cut.closed`/`cells.claimed` transaction and an actual `run.status === 'won'` in this attempt. A button press or demonstration is insufficient.
2. Lesson 2's **separator seen** step requires a closure whose before-step live-trail set is exactly `D`, whose newly claimed set is exactly `D`, whose `D` cells change FIELD→SAFE, and whose two enemy center cells remain FIELD. Then **empty region revealed** requires a later closure with before-step trail exactly `H(h)` and newly claimed set exactly `R(h)` for an allowed row. The rectangle changes FIELD→SAFE, its cells outside `H(h)` establish actual fill, `garden` becomes captured and the run wins. Compare sets, not array order. Retained divider credit survives a nonterminal failed second cut because that safe divider actually remains; Retry/new lesson starts a fresh observer.
3. Lesson 3 completes on an actual win with its required objective captured. Failure feedback is conditional: only a real failure/recovery transaction that preserves prior claimed cells may say that territory was kept. A terminal loss instead uses the existing [retry explanation](retry-feedback.md). Shield, Impact and arbitrary equipment predicates are outside this fixed Scout course.

These strict patterns intentionally describe the taught example, not every valid Xonix solution. If a different legal route wins before the lesson 2 demonstration is observed, show **“Picture revealed; the suggested example was not completed.”** Keep truthful partial steps and offer Retry, Skip lesson and Exit. Never fabricate completion, suppress the legitimate win, block all navigation or call an arbitrary small capture a separator. If the observer cannot verify its context or facts, show guidance unavailable and retain ordinary play/retry/exit without awards.

`cut.closed.cells` currently means **all newly secured cells**, not live-line length. `cells.claimed.indices` is exact; pre-step trail plus the explicit authored sets proves the intended distinction. Check cells entered on the closure tick through those full claimed-set and ownership comparisons. Do not reuse `eventFeedback`'s `< 50` message heuristic, call private trace helpers, or add simulation events for teaching.

### Feasibility probes already performed

An ephemeral Node 22.22.2 probe constructed these geometries from First Signal, used `validateLevel`, then `createRun`/`stepRun` and `createRecorder`/`recordInput`/`exportReplay`/`verifyReplay`. It wrote no files and made no external state edits. Both policies produced matching public replay checkpoints:

| Lesson       | Normal inputs, one tick = 1/120s       | Observed outcome in both policies                                                                                                                                |
| ------------ | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Close line   | Down until terminal                    | Win at tick 414, three lives, 816 claimed cells (52.17%).                                                                                                        |
| Empty side   | Down 420, Up 216, Left until terminal  | Divider at tick 414: 34 cells; second closure/win at tick 918: 391 new cells, 425 total (27.17%). Before those closures, trails contain exactly 34 and 23 cells. |
| Picture home | Down 420, Up 216, Right until terminal | First closure/objective at tick 414; win at tick 906, three lives, 1,190 total cells (76.09%).                                                                   |

A further ephemeral core probe covered rows 16–24 in both policies: all 18 normal-input runs won, with exact `H(h)` before-closure trails and `R(h)` newly claimed sets. These are feasibility results, not committed fixture expectations, browser controls or human difficulty measurements. Implementation must save reproducible legal proof inputs with the final names/normalized identities and cover failures and alternate wins as well.

## Mounting and persistence contract

Use a finite query entry in the actual solo app: `?course=first-flight&lesson=close-line`. Supported lesson values are exactly the three above; omitted lesson means the first. An optional finite `turn-policy=immediate|grid-center` lets existing preview tools select their policy; ordinary course entry otherwise uses the validated saved policy. Unknown/duplicate course values and conflicting `practice=1` input fail visibly before normal-game boot, never silently fall back to an awarding campaign. No map JSON, arbitrary return URL or executable lesson metadata comes from the query.

Resolve the trusted registry through existing scenario validation **before profile-writer acquisition**. `courseSession` is immutable for that document and contributes to the existing `practiceSession` boundary. Scenario changes, ordinary mission selection, Watch first cut, imports and restore actions cannot unset it. Hide irrelevant campaign/library/hangar controls and guard their handlers; hidden DOM alone is not an authority boundary. Keyboard/controller/appearance/audio preferences may be read and changed in memory, but course operations cannot write library, packs, backup journal or suspended-attempt stores, submit mastery work or award even session-only campaign progress. A normal input replay export may remain available and clearly identifies a training map.

Selecting a lesson or policy replaces only the trusted course scenario, creates a fresh run/recorder/observer and returns to **Ready**. It does not require or modify `revealline.playground.current`. Current lesson steps and three per-visit completed/skipped markers stay in memory. Reload explicitly starts the requested lesson afresh; no course save schema or inferred achievement is introduced. Skipping an uncompleted lesson records skipped, never completed; a prior genuine completion in the same visit may remain labeled “completed earlier this visit.”

**Entry from an ordinary active flight is a checked handoff:**

1. Install an entry-in-progress gate, freeze/release input and pause sound **without invoking an entry-triggered autosave**. A narrowly scoped no-save pause path may reuse current pause presentation; ordinary callers retain their semantics. Inspect any existing suspended-slot bytes with JSON parsing and the strict `snapshotSession` envelope preflight before writing; malformed/unsupported envelopes prevent the handoff and stay untouched. Opening Help earlier may already have performed its normal autosave; that separate prior boundary cannot be retroactively preserved. During asynchronous work, direction activity, Back/Menu resume, class changes or another launch cannot advance/replace the run. Cancel remains available and leaves it paused.
2. For an unfinished started real run, create its normal suspended snapshot and verify it through `restoreSession` against the installed campaign. Discard the reconstructed run; it is verification, not adoption. Retain the original run/recorder/ID and a cancellation/context ticket throughout.
3. Recheck writer, generation, backup-lock/journal, successful stored-profile/content adoption, current run identity and checkpoint; use the existing backup-operation lock for the final storage check/write/readback boundary. An unreadable profile, packs or journal must not be repaired or overwritten by course entry. Call `saveSession` and require its explicit `ok === true`. Read the actual stored envelope back and compare its canonical data with the verified snapshot. `persistAttempt()` returns a session even on write failure, and `pause(true)` suppresses autosave errors: **neither is proof that navigation is safe**.
4. Only then navigate to the fixed relative course URL. If recording, verification, quota, readback or ownership fails, remain on the current paused flight with the actual error and its existing export/return controls. Do not discard it, overwrite corrupt storage or make a failed handoff look successful. Ready/terminal entry needs no new flight save and must leave an existing suspended slot alone.

An earlier ordinary Help autosave may have updated the slot before course entry was requested. This plan does not change that behavior. The course-specific entry path itself checks the current slot before writing and establishes a newly verified current-flight checkpoint. Keep its no-save gate active through cancellation/error; subsequent ordinary player actions retain their normal save semantics. A successful navigation may run the existing pagehide save again for the same retained checkpoint/timestamp update. Ready/terminal course entry performs no flight save and leaves any old malformed slot unchanged. Do not promise byte-identical storage across the earlier normal autosave or final same-checkpoint pagehide boundary. Establish the no-write comparison after the retained checkpoint/entry transition, then prove that course wins, losses, settings, skipping and exit leave it unchanged. A session-only active flight that cannot establish a retained checkpoint must not be navigated away automatically; the course remains available from Ready.

Top-level **Return to the game** releases course inputs and navigates to a fixed relative normal-game URL with course/query parameters removed. It never loads/starts the saved flight automatically. Avoid `history.back()`: the existing BFCache path deliberately returns the old document without reclaiming its profile writer. Returning to the normal page permits the ordinary explicit Load saved flight/Resume flow. Inside Playground or Controller Lab, Exit ends the course locally and points to the parent's existing game link; it must not turn the iframe into an awarding game. Keep the existing [practice navigation guard](../game/ui/practice-navigation.mjs) for all other links.

## Course UI and control lifecycle

Course phases are `ready`, `playing`, `paused`, `review`, `switching`, `leaving` and `ended`; derive run completion only from actual terminal state. Current learning-step changes while playing are non-pausing. No intermediate success overlay may merely set `paused=true` on a running run: existing direction activity and controller Back/Menu can resume a paused flight. Review applies only to actual won/lost runs; switching/leaving/ended gates explicitly prohibit sampling commands into physics or implicit resume.

Capture before facts, advance exactly one fixed step, preserve recovery input handling, record that real command, and then publish the after-step observation. Do not change recorder ticks or break a live-cut frame merely because a guidance step changed. Every Retry, Skip, lesson selection, reader transition, reload, blur and disconnect follows current input release/neutral rules. Next lesson prepares Ready and requires a separate Start; Retry retains the existing explicit fresh-attempt start. Held Confirm must not become Start/ability input in the new state. Controller Back/Menu never implies Skip/Next/Exit; reader exits retain their existing end-only behavior.

Reuse the existing two readable surfaces: concise current task beside the board, full course steps in Mission brief/its reader, and actual result/Retry text in Mission details. Done ends reading only. Use current remapped key/glyph labels, real direction/Stop buttons, Hold/Tap and controller Boost Hold/Toggle. The course does not implement another input adapter. Instructions have no expiry; essential guidance remains visible or reviewable without waiting for narration.

Keep 44px targets and the new normal-flow layout. At 320px and short landscape, concise guidance may wrap and the document may scroll vertically; avoid adding a fixed toolbar over the board/control rail. Test the actual instruction/result/reader content, not empty placeholder labels.
