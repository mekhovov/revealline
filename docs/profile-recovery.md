# Read-only profile recovery

This first source slice adds `game/profile-recovery.html`, a separate recovery screen for the current compatible reader. It does not change ordinary game startup, select a different save slot in `app.mjs`, or wire a migration action into Settings. Release packaging and historical-profile qualification remain separate work. A [scoped native check](verification/round-47/profile-reader-native.md) verified one current-version profile export and return to its own paused game.

The screen reads the built release's `game/build-info.json` to identify its current version. An unbuilt source page without that information refuses to begin profile discovery and keeps Back available. The page does not import the ordinary game host. It reuses native controls and the existing controller navigation adapter; the controller animation loop only routes UI focus.

Choose **Find profiles**, select an exact channel and choose **Review**. The reader discovers bounded localStorage keys and keys in the existing assets database. Literal `release-v0.39.0` and `release-0.39.0` channels remain separate. Legacy `release`, current-version channels, and protected development/future channels are labeled without merging them. Discovery checks at most 4096 keys in each storage source and 96 exact channels. It reads no profile values until Review. Unsupported namespaces or inaccessible stores are reported; discovery is never a device-wide media claim inventory. Existing Copy-from-earlier-release transfer retains its separate 32-candidate policy.

Review holds the exact channel's existing writer and backup Web Locks with `ifAvailable`; a busy profile refuses. It reads raw profile/session/backup-lock strings and four exact asset keys: packs, external index, backup journal and external journal. The asset reader opens no requested DB version and aborts any creation upgrade. It never opens the shared soundtrack/media database, creates a store, starts a write transaction or repairs recovery data. Per-key count plus get distinguishes absent values, stored null and stored unsupported undefined.

Before and after checks compare the selected snapshot while the locks are held. Profile structure is validated independently with the existing library validator; a malformed or unsupported flight does not erase a readable profile overview. Counts are structural metadata, not historical execution or first-earned ownership certification. Missing or incompatible assets do not automatically become an empty profile. Original media and saved-flight inspection remain explicitly uninspected/unavailable.

**Prepare stored-data export** rechecks the exact reviewed snapshot. A changed profile requires another Review. The generated download link contains the selected raw strings and accepted structured pointer/journal values. It does not export originals or constitute a verified complete game-data backup. Raw strings, including their stored wrapper/generation and first-receipt text, are preserved without rewriting storage. JSON pointer values must be bounded, acyclic plain data; unsupported types are never coerced or silently omitted. An incomplete diagnostic identifies unsupported/unreadable components without including them as values, keeps their source data untouched, and is labeled incomplete.

The diagnostic export is bounded to 64 MiB. Individual profile, session and pack values keep their existing read bounds; index review is bounded to 256 KiB and each raw journal to 8 MiB. A larger or unsupported journal stays in storage and produces an incomplete diagnostic. These are reader/export limits, not changes to installed pack, shared media, quota or claim budgets. A pending journal is reported and never executed. Preparing a link does not prove that the browser saved a file; the user activates the native download link explicitly.

Cancel, Back, blur and page closure invalidate pending view results. Operation settlement is prompt even if a previously issued Web Locks callback has not arrived; that eventual callback checks cancellation before any read or second lock and releases its lease. This does not claim that the browser has already delivered every pending native callback. Pending asset work is aborted, late successful opens are closed, and object URLs are revoked on replacement or Close. No late result may make a closed screen writable or expose a stale download. No operation writes an old or current profile, preferences, progress, first-earned receipt, save slot, pack index, originals, schema or reservation.

Full backup, paused-flight verification, historical content recovery, same-origin storage format migration and physical offload remain unavailable. Future migration requires a separately qualified compatible reader, actual bounded cross-profile consumer inventory and explicit origin-wide effects. A newer shared DB version alone would not fence localStorage or the separate assets database. This source slice grants no migration or deletion authority and makes no old-reader compatibility or space-recovery promise.

The focused source check passed 42 cases on Node 22 and the same 42 on Node 20: 22 new reader/assets/view lifecycle cases plus all 20 unchanged profile-transfer regressions. This includes the existing Homeward full JSON payload hashing case, using its header-only test decoder. Formatting and linting passed. These modeled checks do not establish actual browser storage recovery, hardware controller behavior, release packaging, a complete binary backup or migration readiness.

## Shared-media snapshot source boundary

`captureRecoverySnapshot(review)` and `revalidateRecoverySnapshot(snapshot)` are separate source APIs, with no controls or ordinary app wiring yet. A host must register exact channel IDs with their supported historical campaigns and trusted external descriptors. The existing raw overview/export does not require that registry or a shared-media read. Aliases remain distinct; an unavailable catalog, malformed journal or missing original refuses only the stronger snapshot capability.

The new reader opens the existing shared database without a requested version and aborts creation. It accepts understood v2/v3/v4 schemas, including generic media within v3/v4, uses readonly transactions, and performs no reservation cleanup, upgrade or journal execution. It captures owned metadata and immutable Blob handles under the selected writer/backup locks, then rechecks raw profile/asset fingerprints and shared domain generations, ledger and physical-handle metadata. Changes refuse the result; those cooperative channel locks do not fence every older page or provide cross-database atomicity.

This first capability validates catalog and original **metadata**, not original bytes, playback or replay. A content hash stored as an ID is not a verified body hash. Returned snapshots explicitly report unverified originals, unavailable saved-flight inspection and no full backup. Stored picture-owner history never registers a playable campaign. Actual body verification, named backup components and isolated paused inspection remain a separate next boundary.

Read limits retain the 256 MiB shared byte budget, 64 MiB single-source bound and domain metadata limits. This first recovery adapter additionally refuses more than 512 combined physical Blob handles; the ordinary manager permits 512 per physical store, so an otherwise readable library with retained orphans may exceed this narrower recovery capability. It is preserved and its raw profile diagnostic remains available. Nonempty shared reservations, unknown metadata keys, present unsupported values or future schemas refuse without repair.

The focused check passed all 60 cases on Node 22 and all 60 on Node 20: 18 new schema, snapshot/cancellation and catalog-extraction cases, plus 42 unchanged raw-reader/profile-transfer regressions. The runtime sources stayed exact throughout both sequential runs; only 3,759 bytes of existing text fixtures were materialized. The earlier native evidence remains limited to the original raw diagnostic reader; it does not qualify these new shared-media APIs.

## Selected original verification and separate file exports

The next source API prepares one rich still original, independently of the raw diagnostic and strict full snapshot. It has no screen controls or ordinary app wiring. An explicitly registered exact historical channel is required; matching a release label or stored campaign name is insufficient. The existing whole external index still needs its trusted descriptors, exact pack bytes and complete owner/presentation metadata closure. Stored archived owners may validate a picture reference; they do not become executable campaigns or certify a first-earned award.

Use `reviewOriginals(review)` to obtain the reader's immutable choices, then `verifyOriginal(choice)`. A choice retains the complete still-asset record and all its exact stored presentation references. Availability is `available-unverified`, `missing` or `length-mismatch`; no availability label claims a decoded image or verified hash. Structural metadata, schemas, journals, reservations and physical handle limits remain strict. The separate lower-level `originalSnapshot()` reports missing or wrong-length referenced bodies as diagnostics, including unrelated legacy/audio/story references. The existing `snapshot()` and `captureRecoverySnapshot()` still refuse these incomplete inventories. Legacy bytes, audio and story files are not selected still choices.

Verification reacquires the exact channel's writer and backup locks, checks the reviewed raw fingerprint and shared marker, then decodes and hashes a fresh immutable selected Blob through `prepareStillAsset`. The result must match every captured asset field, including provenance, byte length, MIME, dimensions and SHA-256. It rechecks the profile and shared ledger, generations, metadata and handles afterward. A generation marker alone cannot prove body integrity. A trusted constructor decoder can be supplied for a controlled host or test; there is no per-call decoder, hash, filename, key or identity override. Production defaults use the existing browser image decoder and its owned URL cleanup. The normal still limits remain 4 MiB, 8192 pixels per side and 16 million pixels, within the existing shared 256 MiB budget.

Explicitly call `exportOriginalComponent(verified, {component: 'original-file'})` or choose `component: 'identity-report'`. Each call rechecks the exact selection and **verifies fresh selected bytes again**, even when the storage key, length and ledger are unchanged. The original component is the exact PNG or JPEG file; its MIME, extension and bounded filename derive from the verified asset. The separate JSON report is limited to 256 KiB and records the exact channel/fingerprints, asset, validated stored references, schema, revision and domain generations. It states `fullBackup:false`, `earnedReceiptAuthority:false` and `restoreAuthority:false`. It is not an import schema. A report that exceeds its bound refuses independently; a previously prepared original file remains immutable.

These two recoverable files are never a partial `.rlmedia` or complete game backup. The existing `.rlmedia` exporter requires every referenced rich and legacy still body and excludes profiles, packs, audio and story domains. Missing an unrelated original therefore still prevents complete still export, while an explicitly selected intact image and raw diagnostics can remain useful. The selected API neither repairs missing data nor infers that the image was earned by the selected profile. It inspects the shared-origin inventory under that channel's leases.

Choices and verification handles are private to one reader. Copies and foreign handles refuse. Starting discovery, another channel review or another original review invalidates the prior original selection; a new verification invalidates the previous verification handle. Close clears those capabilities and cancels pending work. Timeouts and cancellation settle promptly, discard late decode results and consume late rejections. A successful export is an immutable snapshot of verified bytes, not a promise that uncooperative older code cannot later change storage. Channel leases and before/after fingerprints are not an origin-wide writer fence or an atomic transaction across both databases.

The next concrete wiring step is a finite, reviewed exact-channel registry of historical campaigns and external descriptor identities, followed by separate controls in the recovery screen: review available originals, select one, verify it, and explicitly prepare either file. That view must invalidate the selection on profile change, retain Cancel/Back, own and revoke replacement object URLs, and keep native download activation explicit. It must distinguish a prepared file from a completed browser download. No adoption, paused replay, upgrade, deletion, offload, storage-cap increase or ordinary host-key substitution is included here. Include the new module in that host’s explicit packaging or preview inventory before browser qualification. Native qualification for this selected-original slice is still pending.

The focused selected-original check qualified 86 cases on each supported test runtime: the prior 60 reader/catalog/transfer cases, three new availability-snapshot cases and 23 selected-original cases. Replacing only that fixture copy with `structuredClone` preserved every assertion. Only a 3,271-byte existing text helper was newly materialized; PNG bytes are a tiny fixture, and the JPEG case uses an explicitly controlled header/decoder boundary. These tests do not qualify native image decoding, actual browser storage recovery, completed file downloads, complete backup, packaging or physical offload.
